# «Аким на 5 часов» — архитектура MVP

**Ресурсы:** 3 разработчика × 3 часа = 9 человеко-часов.  
**Цель:** воспроизводимый симулятор с точным расчётом Astana Quality of Life Score и настоящим AI-объяснением.  
**Основание:** оба ТЗ — разделы `Tech1` и `Tech2` приложенного `data.md`.  
**Статус:** проектное решение для реализации; числовые примеры ниже отдельно проверены кодом по формулам ТЗ.

> **Главное решение:** один Next.js-проект, одна страница, два серверных обработчика, статический датасет и чистый TypeScript-модуль расчёта. LLM объясняет готовые результаты, но не считает Score, не определяет валидность и не меняет правила.

## 1. Как трактуем требования

### 1.1. Что необходимо получить к концу трёх часов

Пользователь видит исходное состояние пяти районов, выбирает ровно пять разных мероприятий, указывает районы для локальных мер, укладывается в общий бюджет 100 и получает:

- итоговый Score, изменение относительно базы и разложение формулы;
- показатели районов до и после, критические значения и сработавшие синергии;
- AI-объяснение сильных сторон, рисков, компромиссов и приоритетов улучшения.

Бюджет, исходные показатели и правила одинаковы для всех. Невалидный сценарий не получает Score. Это не пошаговая игра с таймером: название «на 5 часов» не означает, что нужно реализовывать пятичасовой игровой процесс. В `Tech2` задан расчётный горизонт восемь кварталов, а не длительность пользовательской сессии. [ТЗ-1: строки 9–31; ТЗ-2: 207–208, 388–397]

### 1.2. Неоднозначность между двумя ТЗ

| Вопрос | Что написано | Решение для MVP |
|---|---|---|
| Покрытие направлений | `Tech1` говорит о пяти решениях по пяти направлениям. `Tech2` явно разрешает не более двух мер одного направления; его пример содержит две социальные меры и ни одной транспортной | **Рабочее допущение: валидатор следует подробным правилам Tech2.** В интерфейсе доступны все пять направлений, но выбирать по одной мере каждого направления необязательно |
| Названия направлений | В `Tech1`: «озеленение», «социальная инфраструктура», «городской сервис»; в `Tech2`: «Экология», «Соцсфера», «Сервисы» | Сохраняем категории каталога `Tech2`; поясняем соответствие названий в интерфейсе |
| Источник чисел | ТЗ содержит показатели, формулу и округлённые контрольные результаты | Считаем по исходным показателям и формуле, а не возвращаем заранее записанный итог |

Это выбранная интерпретация, а не утверждение, что тексты полностью согласованы. Её нужно явно записать в README и обозначить организаторам. Отдельный пользовательский переключатель правил не нужен. Если организаторы потребуют строго одно решение из каждого направления, меняются одна проверка валидатора и соответствующие тесты. Основной пример `Tech2` тогда станет недопустимым; замалчивать это нельзя. [ТЗ-1: 9–15; ТЗ-2: 365–397]

Для демонстрации предусмотрен также сценарий, который покрывает все пять направлений и проходит обе интерпретации: см. раздел 9.3.

### 1.3. Допущения архитектуры, которых нет в ТЗ

Предполагаем, что команда знакома с React/TypeScript и имеет доступ к одному LLM API. Навыки команды, провайдер AI и площадка размещения в ТЗ не заданы. Выбор Next.js ниже — предложение, а не требование организаторов. Проверка API-ключа и запуска проекта — задача первых 15 минут.

## 2. Границы MVP и стек

| Область | Предлагаемое решение | Почему выбираем для этого проекта |
|---|---|---|
| Приложение | Next.js App Router + React + TypeScript | Интерфейс и HTTP-обработчики в одном репозитории и одном развёртывании |
| Интерфейс | Одна страница, обычный CSS/CSS Modules, локальное состояние React | Без настройки дизайн-системы, глобального хранилища и сложной навигации |
| Бизнес-логика | Чистые функции TypeScript в `src/domain/` | Один код валидации для подсказок UI и обязательной серверной проверки |
| Данные | Типизированные константы в `src/domain/data.ts` | Пять районов и 14 мероприятий не требуют базы данных |
| Внешний ввод | Zod-схема формы запроса + собственный валидатор бизнес-правил | Разделяем некорректный JSON и недопустимый игровой сценарий |
| AI | Один серверный адаптер к доступной модели; основной вариант — OpenAI Responses API | Один вызов на анализ, без агентов, инструментов и истории чата |
| Проверки | Vitest для расчёта и правил; ручной сквозной тест | Сначала защищаем формулу и допустимость сценария |
| Запуск | Локальный Node.js-сервер; публикация на уже знакомой площадке при наличии доступа | Демо не должно зависеть от освоения новой инфраструктуры |

Next.js поддерживает Route Handlers в `app/**/route.ts`, а клиентскую и серверную части можно разделять внутри одного приложения. Эти возможности подтверждены официальной документацией; структура проекта и выбор стека — наше проектное решение. [WEB-1; WEB-2]

**Не делаем в обязательной части:** регистрацию, авторизацию, БД, рейтинг команд, карту/GIS, случайные события, квартальную анимацию, загрузку пользовательских датасетов, чат, RAG, мультиагентную систему, PDF/PPTX-экспорт. Сравнение команд, события и генерация презентации прямо отнесены в `Tech1` к опциональным функциям. [ТЗ-1: 32–37]

**Что остаётся простым:** вместо карты — таблица районов; вместо графической библиотеки — полосы показателей на CSS; вместо сохранения сессии — состояние страницы. Перезагрузка сбрасывает сценарий. Это ограничение MVP, которое нужно сообщить пользователю.

## 3. Схема компонентов и поток данных

```text
Браузер: Simulator
  ├─ каталог 14 мер, выбор района, корзина из 5 решений
  ├─ validateDraft(): бюджет и объяснение ограничений
  ├─ таблица районов и ResultPanel
  └─ ExplanationPanel: loading / AI / fallback
          │
          ├── POST /api/evaluate ──────────────────────────┐
          │                                               ▼
          │                                    parse + validateScenario
          │                                               │
          │                                    simulate + buildReport
          │                                               │
          ◄──────────── числовой Evaluation ───────────────┘
          │
          └── POST /api/explain ───────────────────────────┐
                                                          ▼
                                               повторная валидация
                                               и пересчёт на сервере
                                                          │
                                               explain.server.ts
                                                          │
                                                внешний LLM API
                                                          │
                          ◄──────── текст + mode + scenarioKey
```

Оба маршрута работают в одном приложении. «Отдельный расчётный модуль» означает отдельную папку и ответственность, а не отдельный сервис.

### 3.1. Порядок работы

1. `page.tsx` передаёт в клиентский `Simulator` публичные справочники и базовый расчёт. Отдельный `/api/catalog` для неизменяемого каталога не нужен.
2. Пользователь собирает набор. UI показывает стоимость, остаток, число решений и причины запретов. Отправка доступна только при валидных пяти решениях.
3. `/api/evaluate` проверяет вход, берёт цены и эффекты исключительно из серверного каталога и возвращает расчёт без ожидания AI.
4. UI сразу показывает результат и отправляет тот же снимок решений в `/api/explain`. Сервер повторно проверяет и рассчитывает его; готовые числа от браузера не принимает.
5. AI-ответ появляется отдельным блоком. Ошибка провайдера не уничтожает числовой результат.

При изменении выбора старый результат и AI-текст помечаются устаревшими или скрываются. Запросы привязаны к `scenarioKey`; ответ от предыдущего выбора не должен попасть в текущую карточку. Достаточно снимка запроса, счётчика запросов и `AbortController`; инфраструктура очередей не нужна.

### 3.2. Направление зависимостей

```text
components ──► domain/types, domain/data, domain/validate
api routes ──► domain/*, server/*
server/AI ───► domain/types

domain ──────► только TypeScript, без React, HTTP, LLM и секретов
```

LLM-клиент хранится только в `src/server/`, с `import 'server-only'`. В клиентскую часть не импортируем серверные модули, SDK или секреты. Названия API-ключей не имеют префикса `NEXT_PUBLIC_`. [WEB-2]

## 4. Данные и общий контракт

### 4.1. Версионирование

`MODEL_VERSION = "tech2-v1"` идентифицирует вместе исходные данные, каталог, веса и правила. Это наш технический идентификатор, отсутствующий в исходном ТЗ. При изменении любого из этих элементов версию повышаем.

Сервер не принимает пользовательские бюджет, веса, лаги, эффекты или параметры формулы. Данные не мутируются между запросами. Поэтому каждый сценарий начинается с одного и того же состояния независимо от предыдущих пользователей. [ТЗ-1: 26, 41; ТЗ-2: 389]

### 4.2. Типы, которые фиксируем в первые 15 минут

```ts
export type DistrictId =
  | 'esil' | 'almaty' | 'saryarka' | 'baikonur' | 'nura';

export type Direction =
  | 'transport' | 'ecology' | 'social' | 'safety' | 'services';

export type Indicator =
  | 'T1' | 'T2' | 'E1' | 'E2' | 'S1'
  | 'S2' | 'B1' | 'B2' | 'C1' | 'C2';

export type MeasureId =
  | 'M1' | 'M2' | 'M3' | 'M4' | 'M5' | 'M6' | 'M7'
  | 'M8' | 'M9' | 'M10' | 'M11' | 'M12' | 'M13' | 'M14';

export interface Selection {
  measureId: MeasureId;
  districtId?: DistrictId; // запрещён у городской меры, обязателен у районной
}

export interface ScenarioRequest {
  modelVersion: string;
  selections: Selection[];
}

export interface Measure {
  id: MeasureId;
  title: string;
  direction: Direction;
  scope: 'district' | 'city';
  cost: number;
  lag: number;
  effects: Partial<Record<Indicator, number>>;
}

export interface District {
  id: DistrictId;
  name: string;
  populationShare: number;
  indicators: Record<Indicator, number>;
}
```

В API для городской меры ключ `districtId` отсутствует; `null` и строка `"город"` не используются. В карточке UI при этом выводится понятная подпись «Весь город». Известность ID и зависимость поля района от типа меры обязательно проверяются во время выполнения: TypeScript не валидирует пришедший HTTP-запрос.

### 4.3. Контракт числового результата

| Поле `Evaluation` | Содержимое |
|---|---|
| `modelVersion`, `scenarioKey` | Версия модели и канонический ключ набора |
| `selections` | Проверенный набор, отсортированный по числовому ID меры |
| `budget` | `{ limit: 100, spent, remaining }` |
| `baseline` | Score, `average`, `minimum`, `weakestDistrictIds`, критические пары и значения всех районов до действий |
| `after` | Та же структура после применения сценария |
| `scoreDelta` | `after.score - baseline.score` |
| `indicatorChanges` | Для каждой пары «район × показатель»: `before`, `after`, `delta` |
| `measureEffects` | По каждой мере: стоимость, лаг, реализованная доля и добавки показателей по целевым районам **до общего clip** |
| `synergyEffects` | Отдельные бонусы с указанием пары мер, района и показателя |

`baseline` и `after` имеют одинаковый тип `Snapshot`; район внутри него содержит `id`, `districtScore` и `indicators`. Критическая пара содержит `districtId`, `indicator`, `value`. Для одинаковых минимальных районных оценок возвращаем все `weakestDistrictIds`, а не выбираем один произвольно.

Ключ не обязан быть криптографическим хешем. Достаточно канонической строки вида:

```text
tech2-v1|M5@saryarka|M7@nura|M8@nura|M10@nura|M12@city
```

На сервере ключ строится заново; сортировка числовая, а не лексикографическая. Этот ключ нужен для сопоставления результатов, не для авторизации.

## 5. Валидатор — первая обязательная часть

### 5.1. Два режима, общие проверки

`validateDraft(selections)` допускает от нуля до пяти решений и помогает собрать набор. `validateScenario(selections)` требует ровно пять и используется перед каждым серверным расчётом пользовательского сценария. Общие проверки вынесены в одну функцию, чтобы UI и API не разошлись.

Проверяем в таком порядке:

| Проверка | Условие / код ошибки |
|---|---|
| Известные идентификаторы | `UNKNOWN_MEASURE`, `UNKNOWN_DISTRICT` |
| Корректный район | `DISTRICT_REQUIRED`, `DISTRICT_FORBIDDEN` |
| Число решений | Ровно 5 для финального набора: `DECISION_COUNT` |
| Уникальность | Одна мера максимум один раз, даже в разных районах: `DUPLICATE_MEASURE` |
| Бюджет | Сумма фиксированных цен не больше 100: `BUDGET_EXCEEDED` |
| Направления | Не больше 2 мер одного направления: `DIRECTION_LIMIT` |
| Глобальный конфликт | M1 и M3 запрещены совместно независимо от районов: `INCOMPATIBLE_MEASURES` |
| Локальные конфликты | M4/M7 и M5/M13 запрещены только при одинаковом районе: `DISTRICT_CONFLICT` |

Правила взяты из `Tech2`, строки 325–328 и 388–397. Сначала исключаем неизвестные ID; нельзя обращаться к несуществующей записи каталога. После проверки структуры собираем все применимые ошибки, чтобы пользователь исправил набор за один проход.

Невалидный сценарий возвращает `valid: false`, `score: null` и массив ошибок. Не возвращаем ноль: нулевой Score был бы рассчитанным результатом, а ТЗ требует «не считается».

### 5.2. Поведение UI

При выборе мероприятия показываем цену и фактическую долю эффекта за восемь кварталов. Для районной меры сначала требуется район; городская применяется ко всем районам без селектора. Добавление сверх бюджета, шестой меры или третьей меры направления блокируется с конкретным объяснением.

Удаление решения всегда доступно. При смене района уже выбранной меры повторно проверяем локальные конфликты. Отключённая кнопка должна сопровождаться текстом причины, а не только изменением цвета. Прямой HTTP-запрос всё равно проходит серверный валидатор.

## 6. Расчётный модуль

### 6.1. Последовательность строго по Tech2

```text
Для каждого района d и показателя k:

raw[d,k] = initial[d,k]
         + сумма(effect[m,k] × (8 − lag[m]) / 8)
         + сумма(подходящих синергий)

after[d,k] = min(100, max(0, raw[d,k]))

D[d] = сумма(weight[k] × after[d,k])
D_avg = сумма(populationShare[d] × D[d])
D_min = min(D[d])
N_crit = число пар (d,k), где after[d,k] < 40

Score = 0.7 × D_avg + 0.3 × D_min − N_crit
```

Источник: `Tech2`, строки 207–208, 315–323 и 330–364. `simulate()` получает проверенные ссылки на меры и районы, копирует исходные показатели, применяет эффекты, синергии и формулу. Вычисление базового состояния `simulate([])` — внутренний расчёт для сравнения, **не допустимый пользовательский сценарий из нуля решений**.

### 6.2. Детали, на которых легко ошибиться

- **Один общий clip в конце.** Не обрезаем значение после каждой меры: это могло бы сделать результат зависимым от порядка при сочетании положительных и отрицательных эффектов.
- **Лаг применяется только к эффектам меры.** Не уменьшаем стоимость и не масштабируем синергию. Городская мера даёт одинаковую добавку каждому из пяти районов, но оплачивается один раз.
- **Критический порог строго `< 40`.** Значение ровно 40 штрафа не даёт; считаем пары «район × показатель», а не количество проблемных районов.
- **Не округляем промежуточные значения.** Для UI — два знака, для API и тестов — полная вычисленная точность. Тестовое сравнение чисел допускает погрешность `1e-8`.
- **Не меняем шкалу формулы.** Ограничение `[0,100]` относится к показателям. Дополнительный clip итогового Score, бонус за остаток бюджета, нормализация или новые штрафы в ТЗ не заданы и не добавляются.

Перед расчётом канонизируем порядок мер, чтобы даже порядок суммирования был одинаковым. Ни случайность, ни LLM не участвуют в числовой модели. Эти решения непосредственно следуют из заданной формулы и требования независимости от порядка. [ТЗ-2: 332–364, 389, 396]

### 6.3. Синергии

| Пара | Бонус | Где применяется |
|---|---|---|
| M1 + M2 | T1 +2 | В районе M1 |
| M10 + M12 | B1 +2 | В районе M10 |
| M5 + M6 | E2 +2 | В районе M5 |

«Первая мера пары» — M1, M10 или M5 из определения синергии, а не первая по порядку кликов пользователя. Каждую синергию начисляем один раз. [ТЗ-2: 315–323]

### 6.4. Объяснимость без ложного разложения Score

Вклад меры показываем как добавку конкретных показателей после учёта лага. Синергии выводим отдельными строками. Итоговое изменение показателя берём из `indicatorChanges`, поэтому общий clip остаётся видимым.

Не присваиваем каждой мере выдуманные «+X баллов итогового Score». Из-за минимального района, критического порога, синергий и clip итог нелинеен: сумма независимых оценок мер в общем случае не равна улучшению всего сценария. Это математическое следствие формулы, не дополнительное правило.

## 7. HTTP API

### 7.1. `POST /api/evaluate`

Тело запроса — только версия и решения:

```json
{
  "modelVersion": "tech2-v1",
  "selections": [
    { "measureId": "M7", "districtId": "nura" },
    { "measureId": "M8", "districtId": "nura" },
    { "measureId": "M10", "districtId": "nura" },
    { "measureId": "M12" },
    { "measureId": "M5", "districtId": "saryarka" }
  ]
}
```

Успех: HTTP 200, `{ "valid": true, "result": Evaluation }`. Числовая часть для этого запроса **должна** содержать:

```json
{
  "budget": { "limit": 100, "spent": 95, "remaining": 5 },
  "baseline": {
    "score": 52.55768,
    "average": 56.8624,
    "minimum": 49.18
  },
  "after": {
    "score": 56.54307,
    "average": 58.0776,
    "minimum": 52.9625
  },
  "scoreDelta": 3.98539
}
```

Это сокращённый фрагмент `Evaluation`, не полный контракт: поля районов, критических пар и эффектов определены в разделе 4.3. Значения получены отдельным проверочным расчётом по данным ТЗ.

Пример ошибки после замены M8 на M3: набор M7, M3, M10, M12, M5 стоит 105. Ответ HTTP 422:

```json
{
  "valid": false,
  "score": null,
  "errors": [
    {
      "code": "BUDGET_EXCEEDED",
      "message": "Стоимость 105 превышает бюджет 100.",
      "measureIds": ["M3", "M5", "M7", "M10", "M12"]
    }
  ]
}
```

### 7.2. `POST /api/explain`

Принимает **тот же `ScenarioRequest`**, а не произвольный текст, prompt или результат от клиента. Повторно валидирует и считает сценарий, затем вызывает AI-адаптер. Предыдущий вызов `/api/evaluate` не является условием доступа: сервер самодостаточно проверяет запрос.

Успешный или резервный ответ:

```ts
type ExplainResponse = {
  modelVersion: string;
  scenarioKey: string;
  mode: 'llm' | 'fallback';
  model: string | null; // заполняет сервер; null для fallback
  explanation: {
    summary: string;
    strengths: string[];
    risks: string[];
    recommendations: string[];
  };
  warning?: string;
};
```

Fallback с честной маркировкой можно возвращать HTTP 200: запрос обработан, но AI недоступен. Ошибки входа одинаковы у обоих маршрутов.

| HTTP | Значение |
|---|---|
| 400 | JSON или форма запроса не соответствует схеме; неизвестные поля отвергаются |
| 409 | `modelVersion` отличается от серверной; предложить перезагрузить страницу |
| 413 | Слишком большой запрос; проектный лимит тела — 16 КБ, проверяем фактические байты |
| 422 | Нарушение бизнес-правил; Score не считается |
| 429 | Ограничение частоты запросов на уровне площадки, если оно настроено |
| 500 | Непредвиденная серверная ошибка; без stack trace и секретов в ответе |

## 8. AI: аналитик, а не калькулятор

### 8.1. Что передаём модели

`buildAiContext(Evaluation)` собирает компактный JSON: выбранные меры, цены, лаги, область действия, Score до/после, составляющие формулы, изменения районов и показателей, исчезнувшие и оставшиеся критические пары, эффекты мер и синергии. Можно приложить небольшой каталог, чтобы названия рекомендаций не выходили за исходные 14 мер.

Модель не получает доступ к изменению состояния. Она не вызывает инструменты, не делает веб-поиск и не читает секреты. Один серверный запрос формирует четыре текстовых блока. Такой раздел труда прямо предусмотрен в `Tech2`: LLM получает результат расчёта и объясняет его, а не считает числа. [ТЗ-2: 386]

### 8.2. Основа системной инструкции

```text
Ты объясняешь результаты синтетического симулятора управления городом.
Все факты и числовые результаты бери только из переданного JSON.
Не рассчитывай Score, не меняй бюджет, эффекты, правила и веса.
Не выдумывай новые мероприятия, статистику или реальные последствия.
Объясни общий результат, слабый район, критические показатели,
влияние выбранных мер, лагов, синергий и основные компромиссы.
Если показатель не изменился, не говори, что проблема решена.
Рекомендации формулируй как приоритеты для следующего сценария.
Не обещай улучшение Score для альтернативы, которую не посчитал движок.
Не называй текущий набор оптимальным: глобальная оптимизация не выполнялась.
Отделяй следствия модели от гипотез о реальном городе.
Верни JSON: summary, strengths, risks, recommendations. Язык — русский.
```

Все основные числа UI выводит из `Evaluation`, а не извлекает из текста LLM. Запрашиваем структурированный ответ по JSON Schema и повторно проверяем его форму. Structured Outputs поддерживает заданную структуру, но **не гарантирует фактическую правильность текста**; это прямо оговорено в документации. [WEB-3]

### 8.3. Отказы и ограничения

Предлагаемые настройки: один вызов без автоматических повторов, общий тайм-аут 15 секунд, короткий ответ примерно до 1 200 выходных токенов. Это проектные лимиты, не обещание скорости провайдера. Проверяем в реальном тестовом вызове, что выбранной модели хватает лимита; идентификатор модели хранится в `LLM_MODEL`, а не зашивается в компоненты.

При тайм-ауте, отказе, исчерпанной квоте, неполном или невалидном ответе показываем шаблонное объяснение из расчётных данных и предупреждение **«AI недоступен: показано шаблонное объяснение»**. Оставляем кнопку повторного запроса пользователем.

**Важно:** fallback обеспечивает работоспособность калькулятора, но сам по себе не выполняет must-have «AI-анализ». Для сдачи нужен хотя бы один проверенный настоящий вызов доступной модели. Заранее записанный текст нельзя выдавать за живой AI.

Ключ хранится на сервере в переменных окружения. Не пишем ключи и полные ответы провайдера в публичные логи. Текст отображаем как обычный текст, не вставляем как HTML. Для публичной демонстрации желательно использовать готовое ограничение запросов площадки; без него и без авторизации система не защищена от накрутки расходов. Собственный распределённый rate limiter в эти три часа не строим.

## 9. Проверенные числовые эталоны

Ниже — собственный воспроизводимый пересчёт исходного датасета и формул, а не новые требования. Исходный пример и округлённые ориентиры находятся в `Tech2`, строки 330–385. Проверка выполнена отдельным Python-расчётом с рациональной арифметикой; реализация на TypeScript должна дать те же результаты в пределах указанной погрешности.

### 9.1. База без действий

| Величина | Точное контрольное значение |
|---|---:|
| D Есиль | 62.99 |
| D Алматы | 57.06 |
| D Сарыарка | 54.65 |
| D Байконур | 56.63 |
| D Нура | 49.18 |
| D_avg | 56.8624 |
| N_crit | 2 |
| Score | **52.55768** |

Критические пары: Нура/S1 = 38 и Нура/S2 = 35. В интерфейсе показываем **52.56**, но не используем округлённое число как исходное значение для дальнейших вычислений.

### 9.2. Пример из Tech2

**Набор:** M7 → Нура; M8 → Нура; M10 → Нура; M12 → город; M5 → Сарыарка.

| Величина | Контрольное значение |
|---|---:|
| Стоимость / остаток | 95 / 5 |
| D Есиль после | 63.4275 |
| D Алматы после | 57.4975 |
| D Сарыарка после | 56.3 |
| D Байконур после | 57.0675 |
| D Нура после | 52.9625 |
| D_avg после | 58.0776 |
| N_crit после | 0 |
| Score после | **56.54307** |
| Прирост | **3.98539** |

Промежуточные проверки: Нура/S1 = 48; Нура/S2 = 43.75; Нура/B1 = 67.5, включая синергию +2; Нура/B2 = 51.75. Сарыарка/E2 = 48.75, C1 = 47.5. M12 увеличивает C2 каждого района на 4.375.

Полезное объяснение результата, полностью получаемое движком:

```text
Улучшение общей средней:   0.7 × (58.0776 − 56.8624) = 0.85064
Улучшение слабого района:  0.3 × (52.9625 − 49.18)   = 1.13475
Снятие критических штрафов:                         = 2
Итого изменение Score:                             = 3.98539
```

Это честное аддитивное разложение **частей формулы**, в отличие от попытки произвольно распределить итог по мероприятиям.

### 9.3. Демо с охватом всех пяти направлений

**Набор:** M1 → Нура; M4 → Сарыарка; M7 → Нура; M10 → Нура; M12 → город.

| Величина | Контрольное значение |
|---|---:|
| Стоимость / остаток | 83 / 17 |
| Охвачено направлений | 5 |
| D_avg после | 58.0996 |
| Минимальный D после, Нура | 53.125 |
| N_crit после | 1 — Нура/S2 = 35 |
| Score после | **55.60722** |
| Прирост | **3.04954** |

M4 и M7 находятся в разных районах, поэтому конфликта за участок нет. Этот сценарий полезен для демонстрации охвата всех направлений, но не объявляется оптимальным. Более высокая средняя оценка, чем в примере Tech2, здесь не означает более высокий итоговый Score: сохраняется критический штраф.

## 10. Интерфейс: одна страница, понятный основной сценарий

```text
«Аким на 5 часов»                         Бюджет: 95 / 100
Синтетическая модель * горизонт 8 кварталов

[Транспорт] [Экология] [Соцсфера] [Безопасность] [Сервисы]

Каталог мероприятий                 Выбранные решения: 5 / 5
Название, цена, лаг                 M7 * Нура       [Удалить]
Полный / реализованный эффект       M8 * Нура       [Удалить]
[Выбрать район] [Добавить]           ...
                                    Остаток: 5
                                    [Рассчитать сценарий]

Score: 52.56 → 56.54     Изменение: +3.99
Средний балл * слабый район * критические пары: 2 → 0

Районы: D до / после / изменение
[Раскрыть все 10 показателей]

AI-анализ: итог / сильные стороны / риски / рекомендации
```

Компоненты: `Simulator`, `MeasureCatalog`, `SelectionPanel`, `DistrictTable`, `ResultPanel`, `ExplanationPanel`. В `Simulator` достаточно состояний выбора, расчёта, ошибок и AI-ответа. Отдельный глобальный store не нужен.

Показываем не только красивый Score, но и три составляющие формулы. Для критических значений выводим подпись «ниже 40»; для значения 40 — не ставим критический статус. У неизменившегося показателя дельта нулевая. Русские названия из каталога сохраняем.

Кнопка «Загрузить пример» вставляет проверенные решения, но запускает обычные API и расчёт: это не подстановка готового результата. На демо достаточно двух таких пресетов из раздела 9. Таймер, экран входа и отдельная страница отчёта не нужны.

## 12. План на 180 минут

План — целевой объём работы для команды, знакомой с выбранным стеком, а не гарантия срока при любых исходных условиях. Последние 45 минут не занимаем новыми функциями.

| Время от старта | A — расчёт | B — интерфейс | C — API/AI/сдача | Контрольный результат |
|---|---|---|---|---|
| 00–15 мин | Согласовать типы, правила и неоднозначность ТЗ | Согласовать состав экрана и API-контракт | Создать проект; проверить ключ и один реальный LLM-вызов; зафиксировать зависимости | Проект запускается; типы и пример ответа общие |
| 15–45 мин | Перенести 5 районов и 14 мер; реализовать валидатор | Каталог, селектор районов, корзина, бюджет | Реализовать форму двух API на fixture; схему запроса; AI-адаптер | UI собирает набор; API и AI проверены по отдельности |
| 45–75 мин | Эффекты, лаги, синергии, clip, Score; тесты базы и примера | ResultPanel и DistrictTable на общем fixture | Обработка AI-ошибок, fallback, `.env.example`; первый черновик README | Эталон даёт 56.54307; результат отображается |
| 75–105 мин | Подключить отчёт с дельтами и трассировкой эффектов | Подключить настоящий `/api/evaluate`, сообщения валидатора | Подключить настоящий движок к обоим API; AI-контекст | Первый полный сценарий: выбор → расчёт → AI |
| 105–135 мин | Граничные проверки и конфликты | Сброс устаревших ответов, два демо-пресета, состояния загрузки | Проверить сборку; закончить README; проверить локальный запуск и доступную площадку | Основной сценарий работает без fixture-подмен |
| 135–165 мин | Совместная интеграционная проверка; исправить расчётные ошибки | Прогнать сценарии пользователя; исправить блокирующие проблемы | Проверить свежий запуск, секреты, доступность API и AI | Функциональная заморозка; никаких новых фич |
| 165–180 мин | Проверить контрольные числа на сборке | Провести демо-прогон | Финальная сборка, репозиторий, инструкция, ссылка при наличии | Решение готово к проверке |

**Жёсткий контроль:** к 105-й минуте должен работать сквозной путь с настоящим AI. Если не работает, убираем полировку, графику и все дополнительные функции. Не сокращаем валидацию, тесты эталонов, реальный AI-вызов и README.

**Если API-ключ не работает в первые 15 минут:** C сразу проверяет другой уже доступный провайдер или доступ команды. Не откладываем этот риск до последних минут и не считаем fallback выполненным AI-требованием.

## 13. Минимальная матрица тестов

Тесты ниже разделяют внутренние проверки движка и публичную проверку сценария. Для проверки изолированного эффекта допустим прямой вызов `simulate()` с неполным набором; публичный API такой набор не принимает.

| Тест | Ожидаемое поведение |
|---|---|
| Целостность данных | 5 районов, 14 уникальных мер, 10 показателей; суммы весов и долей населения равны 1; диапазоны показателей 0–100 |
| Внутренняя база | `simulate([]).score ≈ 52.55768`, критических пар 2 |
| Пример Tech2 | Валиден; стоимость 95; Score ≈ 56.54307; критических пар 0 |
| Все пять направлений | Пример 9.3 валиден; стоимость 83; Score ≈ 55.60722 |
| Граница бюджета | M3/Нура + M6/город + M7/Нура + M10/Нура + M12/город: стоимость ровно 100, допустимо |
| Превышение бюджета | Пример ошибки раздела 7.1: стоимость 105, HTTP 422, Score = null |
| Количество решений | Публичные запросы с 0, 4 или 6 решениями отвергаются |
| Повтор меры | M10 в двух разных районах всё равно запрещён |
| Лимит направления | M7 + M8 + M9 + M11 + M12: три социальные меры, запрещено |
| Область действия | Локальная мера без района и городская с районом отвергаются; неизвестный ID не вызывает падение |
| M1 / M3 | Совместно запрещены, даже если районы разные |
| M4 / M7 | Одинаковый район — запрещено; разные районы — разрешено при остальных выполненных правилах |
| M5 / M13 | Аналогичная отдельная проверка совпадения районов |
| Лаг | M7 даёт S1 +10, M12 даёт C2 +4.375 каждому району, M11 даёт T1 −1.75 |
| Все три синергии | У каждой пары ровно один фиксированный бонус +2 в нужном районе; без второй меры бонус отсутствует |
| Граница критичности | 39.999 — критично, 40 — не критично; считаем отдельные пары |
| Clip и отрицательные эффекты | На отдельном тестовом датасете обрезаем после общей суммы; результат остаётся в 0–100 |
| Независимость порядка | Все перестановки одного набора дают одинаковые значения и `scenarioKey` |
| Изоляция пользователей | Повторный расчёт не меняет исходные данные и не накапливает эффекты |
| Подделка клиентских данных | Поля `budget`, `score`, `effects` и неизвестные ключи отвергаются схемой; сервер берёт каталог сам |
| Версия модели | Несовпадение версии возвращает 409 |
| Сбой AI | Числовой результат остаётся; `mode: fallback` и явное предупреждение |
| Устаревший ответ | AI для прежнего набора не показывается рядом с новым результатом |

Критические тесты автоматизируем в первую очередь: база, оба эталона, бюджет, пять решений, уникальность, категории, конфликты, лаги и синергии. Проверки интерфейсных гонок и внешнего AI достаточно пройти вручную. Ни один обычный unit-тест не должен требовать API-ключ или интернет.

## 14. README, воспроизводимость и критерии готовности

README и воспроизводимость оцениваются отдельно в 25 баллов из 100; столько же дают соответствие задаче и техническая реализация. Поэтому документация — часть обязательной поставки, а не оставшаяся на потом формальность. [ТЗ-1: 48–68]

Будущий README должен содержать цель симулятора, стек, схему компонентов, выбранную интерпретацию направлений, формулу, источник синтетических данных, контрольные числа, ограничения MVP и инструкции запуска. Зафиксировать фактически проверенную версию Node.js и зависимости в lockfile; не писать непроверенные номера версий.

Предусмотреть в `package.json` команды `dev`, `build`, `start`, `test`. Инструкция запуска после реализации:

```bash
npm ci
cp .env.example .env.local
# Заполнить ключ и ID модели в .env.local.
npm run test
npm run dev

# Проверка production-сборки:
npm run build
npm run start
```

`.env.example` содержит только имена переменных и пустые значения:

```dotenv
OPENAI_API_KEY=
LLM_MODEL=
```

Без ключа приложение запускает калькулятор и явно показывает fallback. Для полного AI-режима требуется реально работающая конфигурация. Секреты исключены из Git. Установка после клонирования должна проходить через `npm ci`, а не через обновление зависимостей до произвольных последних версий.

- [ ] Реальный LLM-вызов даёт связанное с текущим сценарием объяснение; fallback не маскируется под AI.
- [ ] Изменение решения пересчитывает результат; порядок выбора не влияет на него.
- [ ] Репозиторий запускается по README; production-сборка проходит; ключей в Git нет.

**Демо-последовательность:** открыть базу 52.56 → загрузить пример Tech2 → показать 95/100 и результат 56.54 → объяснить снятие двух критических штрафов → показать настоящий AI-анализ → заменить M8 на M3 и получить отказ из-за бюджета 105 → загрузить пример всех направлений и показать другой Score. Это проверяет основной сценарий, ограничения и объяснимость без дополнительных экранов.

## 15. Развитие после обязательной части

При полностью готовом MVP первым дополнением можно сделать «Проверить одну замену»: программа перебирает замену одной из пяти мер или её района, проверяет каждый полученный набор и сравнивает Score. В каталоге 54 конкретных варианта действия: 10 районных мер × 5 районов + 4 городских. Наивная верхняя граница — 5 × 54 = 270 кандидатов до фильтрации. Это наш вывод из каталога, не требование ТЗ. LLM только объясняет найденный движком вариант; локальное улучшение не называется глобальным оптимумом.

Сохранение сценариев, сравнение команд, события и презентации — последующие итерации. База данных появится при необходимости хранить сценарии и результаты, а не заранее. Расчётный модуль при этом останется независимым от хранения и провайдера AI.
