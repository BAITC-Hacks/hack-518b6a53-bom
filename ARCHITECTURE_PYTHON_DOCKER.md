# «Аким на 5 часов» — архитектура на Python в Docker

**Редакция:** 23 сентября 2026 года.  
**Ограничение:** 3 разработчика, 3 часа на MVP.  
**Основание:** `data.md` с разделами Tech1 и Tech2; ранее подготовленный `ARCHITECTURE.md`; уточнение о Python и Docker.  
**Статус:** проектное решение. Документ описывает устройство системы, а не готовую или проверенную сборку.

> **Выбранная схема:** три постоянно работающих контейнера — `ui` на Streamlit, `api` на FastAPI и `llm` с локальной моделью через Ollama. Расчёт, правила и подготовка объяснения находятся внутри одного Python-backend. Базы данных, очереди и отдельных расчётных микросервисов нет.

## 1. Что меняется и что сохраняется

| Область | Решение новой редакции |
|---|---|
| Язык собственного кода | Python: интерфейс, API, расчёты, валидация, AI-адаптер и служебные скрипты |
| Интерфейс | Streamlit вместо Next.js/React; отдельный JavaScript-проект не создаём |
| Сервер | FastAPI; бизнес-логика остаётся обычными Python-модулями, а не набором сетевых сервисов |
| Развёртывание | Один репозиторий, один Docker Compose-проект, один Docker-хост |
| AI | Локальная модель в контейнере Ollama вместо обязательной зависимости от внешнего LLM API |
| Данные | Версионированные JSON-файлы, включённые в образ API |
| Числовая модель | Формула, исходные показатели, цены, лаги, синергии и ограничения Tech2 не меняются |
| Сохранение | Пользовательский сценарий живёт только в сессии интерфейса; постоянная история не предусмотрена |

Streamlit, FastAPI и Ollama — **архитектурный выбор**, а не технологии, заданные ТЗ. Сохраняется принцип предыдущей архитектуры: LLM объясняет рассчитанные результаты, но не определяет валидность и не вычисляет Score. [ТЗ-2, §3; АРХ-1, §§3, 6–8]

**Граница «всё в Docker».** Интерфейс, API, локальный AI, подготовка модели и тестовые запуски выполняются в контейнерах. На хосте нужны Docker Engine / Docker Desktop и Compose; локальные Python, Node.js и Ollama не требуются. Браузер, Docker и при необходимости драйвер GPU остаются на хосте. Готовый сервер Ollama — инфраструктурная зависимость, а не собственный Python-код. [W1, W4]

**Граница MVP.** Не включаем авторизацию, историю сценариев, рейтинг команд, карту, RAG, агентов, обучение модели, случайные события и экспорт презентаций. Сравнение команд, события и презентации в Tech1 опциональны. Отсутствие постоянного хранения — выбранное ограничение MVP. [ТЗ-1, раздел «Опционально»]

## 2. Контейнерная схема

```text
Браузер пользователя
        │ HTTP + встроенное WebSocket-соединение Streamlit
        ▼
┌───────────────────────────────┐
│ ui                            │
│ Python + Streamlit            │
│ Экран, формы, состояние сессии │
│ Порт контейнера: 8501         │
└───────────────┬───────────────┘
                │ HTTP/JSON: http://api:8000
                │ Сеть app_net
                ▼
┌────────────────────────────────────────────┐
│ api                                        │
│ Python + FastAPI + Uvicorn                  │
│                                            │
│ HTTP-контракты → валидация → расчёт → отчёт │
│                              │             │
│                       AI-адаптер            │
│ Датасет и каталог: read-only                │
│ Порт контейнера: 8000                       │
└──────────────────────────────┬─────────────┘
                               │ HTTP/JSON: http://llm:11434
                               │ Сеть llm_net
                               ▼
                 ┌───────────────────────────┐
                 │ llm                       │
                 │ Ollama + локальная модель │
                 │ Только генерация текста   │
                 │ Порт контейнера: 11434    │
                 └─────────────┬─────────────┘
                               │
                       volume: ollama_data
                       → /root/.ollama

model-init — разовый Python-контейнер на образе api:
проверяет / загружает модель через HTTP в llm и завершается.
```

Имена `api` и `llm` — DNS-имена сервисов Compose. Браузер к ним не обращается: HTTP-клиент находится в Python-процессе `ui`. Межконтейнерные обращения используют внутренние порты, а не порты хоста. [W2, W3]

## 3. Что находится в каждом контейнере

### 3.1. `ui` — интерфейс на Python

| Параметр | Содержание |
|---|---|
| Основной процесс | Streamlit, запускающий `frontend/app.py` |
| Собственный код | Каталог, выбор района, список решений, бюджет, таблицы результатов, блок AI-объяснения |
| Зависимости | Python 3.12 как выбранная базовая ветка, Streamlit, HTTPX, Pydantic |
| Получаемые данные | Каталог, базовое состояние, проверки черновика, расчёт и объяснение из API |
| Состояние | `st.session_state`: текущие решения, результат, объяснение, ключ сценария и ошибки |
| Сеть | Только `app_net`; адрес API — `http://api:8000` |
| Публикация | Для локального демо: `127.0.0.1:8501:8501` |
| Постоянное хранилище | Нет |

**Не содержит:** формулу Score, собственную копию правил, отдельный файл исходного датасета, LLM-клиент и прямой доступ к Ollama. Значения бюджета и цен показывает из API, а не из независимых констант интерфейса.

Вместо дублирования валидатора UI отправляет кандидатный набор в `/api/v1/validate`. Счётчики можно отображать локально, но разрешение изменения набора и окончательная проверка принадлежат API.

Streamlit поддерживает контейнерный запуск и собственный health endpoint. Состояние сессии связано с WebSocket-соединением; после перезагрузки вкладки оно сбрасывается. Это ограничение явно показываем пользователю. Выбор одного пользователя не помещаем в глобальную переменную или общий кеш: пользовательские данные хранятся только в его сессии. [W1, W3]

### 3.2. `api` — единственный владелец бизнес-логики

| Параметр | Содержание |
|---|---|
| Основной процесс | Один Uvicorn worker с приложением `backend.main:app` |
| Собственный код | HTTP-маршруты, схемы, загрузка данных, валидатор, симулятор, отчёт, AI-адаптер и шаблонное объяснение |
| Зависимости | Python 3.12, FastAPI, Uvicorn, Pydantic, HTTPX |
| Исходные данные | `/app/data/tech2-v1/`, копируются в образ и не изменяются во время работы |
| Состояние | В памяти — неизменяемый датасет, базовый расчёт, HTTP-клиент и ограничитель AI-вызовов |
| Сеть | `app_net` и `llm_net` |
| Публикация | Порт `8000` на хост по умолчанию не публикуется |
| Постоянное хранилище | Нет |

Внутри контейнера четыре логические части: HTTP-слой, прикладные сценарии, расчётное ядро, адаптеры данных и LLM. Это **модули одного процесса**, не четыре контейнера.

На запуске API загружает и проверяет датасет, рассчитывает базовое состояние, создаёт HTTP-клиент. На остановке закрывает клиент. Ошибочный датасет не исправляется автоматически и не заменяется демоданными: API сообщает о неготовности.

Один worker — сознательное ограничение этой архитектуры. Оно позволяет использовать простой процессный лимит одновременных AI-запросов. FastAPI запускается в собственном Python-образе; дополнительный процессный менеджер не закладываем. [W5]

### 3.3. `llm` — локальная генерация объяснения

| Параметр | Содержание |
|---|---|
| Образ | Официальный `ollama/ollama`, конкретный релиз и digest фиксируются при сборке окружения |
| Основной процесс | Сервер Ollama |
| Модель | Одна локальная instruction-модель; идентификатор задаётся через `LLM_MODEL` |
| Вход | Подготовленные API факты расчёта и инструкция формата ответа |
| Выход | Структурированное текстовое объяснение |
| Сеть | Только `llm_net`; слушает `0.0.0.0:11434`, без публикации порта на хост |
| Хранилище | Именованный том `ollama_data`, смонтированный в `/root/.ollama` |
| Облачные функции | Отключены через `OLLAMA_NO_CLOUD=1` |

В контейнере нет валидатора сценария, расчётной формулы, интерфейса или HTTP API проекта. Модель не получает инструменты, доступ к файлам проекта или возможность менять результат.

Официальный образ поддерживает CPU-режим; GPU требует соответствующей конфигурации хоста и контейнера. Размер модели, потребление памяти и приемлемое время генерации **не определены в ТЗ и не проверены на машине команды**. Конкретную модель нельзя считать выбранной только по названию: требуется проверка русского объяснения и JSON-ответа на целевом оборудовании. [W4, W6]

### 3.4. `model-init` — подготовка модели, не постоянный сервис

Разовый контейнер использует **тот же образ, что `api`**, но запускает `scripts/init_model.py`, а не Uvicorn. В нём находится только выполняемый Python-сценарий подготовки; отдельный образ с ещё одним сервером не нужен.

Он ждёт доступности Ollama, проверяет наличие выбранной модели, при отсутствии инициирует загрузку через `/api/pull`, сверяет digest с ожидаемым значением, когда оно задано, и выполняет небольшой пробный запрос. После успеха завершается с кодом `0`; при ошибке — с ненулевым кодом. Повторный запуск не должен без необходимости обновлять уже подготовленные веса. [W7, W8]

Том весов монтируется **только в `llm`**: `model-init` работает через HTTP, а не пишет в каталог Ollama напрямую. У него нет опубликованных портов; политика перезапуска — `no`. Его успех не является условием запуска калькулятора.

Тесты также запускаются разово внутри Python-контейнеров соответствующих образов с тестовыми зависимостями. Постоянного контейнера `tests` нет; проверки ядра и API используют подмену LLM и не зависят от скачивания модели.

Вложенные Python-пакеты также содержат `__init__.py`; повторяющиеся файлы в дереве опущены. Файлы `.lock` здесь — полностью зафиксированные списки зависимостей, пригодные для установки через `pip -r`, а не обещание конкретного формата стороннего менеджера.

**Контекст сборки обоих образов — корень репозитория.** В `api` копируются `backend/`, `shared/`, `data/` и `scripts/`; в `ui` — только `frontend/` и `shared/`. Для обоих задаются `WORKDIR=/app` и `PYTHONPATH=/app`, чтобы импорты общих схем работали одинаково. `docs/` и тесты не нужны в рабочих слоях образов; тестовые цели добавляют их отдельно.

## 5. Границы модулей

```text
frontend/app, views, state ──► frontend/api_client ──► HTTP API
          │                            │
          └────────────────────────────┴──► shared/schemas

backend/routes ──► backend/services ──► backend/domain
       │                   │
       ▼                   ├──► adapters/dataset
shared/schemas             ├──► adapters/llm
                           └──► adapters/fallback

backend/domain ──► стандартная библиотека Python
```

`domain/` не импортирует FastAPI, Streamlit, HTTPX и код провайдера. Он получает данные аргументами и возвращает результат, не выполняет сетевые запросы и не читает переменные окружения. Подготовку данных и преобразование между доменными структурами и HTTP-схемами выполняет прикладной слой.

`shared/schemas.py` задаёт форму сообщений, но **не содержит копию бизнес-валидатора**. UI и API собираются из одной версии этих схем. Отдельного пакета в реестре, RPC-фреймворка или сервиса контрактов нет.

`services/scenarios.py` используется и при обычном расчёте, и при AI-анализе. Поэтому оба пути проверяют одинаковые правила и получают одинаковые числа. Отдельная абстракция репозитория, ORM или универсальный DI-контейнер в MVP не нужны.

## 6. Владение данными и расчётные инварианты

### 6.1. Где находится состояние

| Данные | Владелец и место | После перезапуска |
|---|---|---|
| Исходные районы, каталог, правила | Файлы внутри образа `api`; проверенные структуры в памяти | Восстанавливаются из той же версии образа |
| Базовый расчёт | Память `api` | Пересчитывается из исходных показателей |
| Выбранные решения и последний ответ | Сессия `ui` | Не сохраняются |
| Весовые файлы LLM | Том `ollama_data` | Сохраняются, пока том не удалён |
| Логи | stdout/stderr контейнеров | Хранение и ротация определяются Docker-хостом |

PostgreSQL, SQLite и Redis в этой схеме отсутствуют. Это не «временная БД в JSON»: JSON-файлы — неизменяемый справочник, пользовательские записи в них не добавляются.

`tech2-v1` — версия **симуляционной модели**: данных, правил и формулы. Она не обозначает версию LLM. Изменение бизнес-данных требует новой версии; замена языковой модели не должна менять Score. [АРХ-1, §4.1]

### 6.2. Что обязательно остаётся внутри ядра

| Инвариант | Архитектурное следствие |
|---|---|
| Бюджет 100; ровно 5 уникальных мероприятий; максимум 2 из направления | Окончательная серверная проверка перед каждым пользовательским расчётом |
| Район обязателен только для районной меры | Сервер сверяется с каталогом, а не доверяет переданному клиентом типу меры |
| M1/M3 несовместимы глобально; M4/M7 и M5/M13 — в одном районе | Конфликты централизованы в правилах и одном валидаторе |
| Горизонт 8 кварталов; доля эффекта `(8 − lag) / 8` | Стоимость не масштабируется лагом; городская мера оплачивается один раз |
| Синергии фиксированные и лагом не масштабируются | Ядро применяет их отдельно, в районе указанной в ТЗ первой меры пары |
| Порядок решений не влияет на результат | Каноническая сортировка мер; сумма всех эффектов и синергий перед общим `clip` |
| `Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit` | LLM не участвует в расчёте; критичность — строго `< 40` для каждой пары «район × показатель» |
| Невалидный набор не получает Score | Не возвращаем вычисленный результат, ноль или штрафной заменитель |

Основание инвариантов: Tech2, §§2–4. Производные требования к организации кода — предложенное обеспечение этих правил. [ТЗ-2]

Каждый расчёт начинается с новой копии исходных показателей, а не с результата предыдущего запроса. Промежуточные значения не округляем; два знака используются только при отображении. Базовый расчёт без мер — внутренний ориентир, а не допустимый пользовательский сценарий. [АРХ-1, §§4.1, 6]

В отчёте вклад мероприятия означает изменение показателей с учётом лага **до общего ограничения диапазона**. Синергии и фактическая итоговая дельта показываются отдельно. Из-за нелинейных частей формулы не приписываем каждой мере произвольный независимый вклад в итоговый Score. [АРХ-1, §6.4]

## 7. Контракты API

### 7.1. Маршруты

| Маршрут | Вход | Результат |
|---|---|---|
| `GET /api/v1/catalog` | Нет | Версия, районы, каталог, публичные правила, базовый расчёт и пресеты |
| `POST /api/v1/validate` | Версия и текущие решения | Проверка черновика: допустимость, возможность расчёта, стоимость, остаток, ошибки; без Score |
| `POST /api/v1/evaluate` | Версия и ровно 5 решений | Проверка и числовой отчёт; без вызова LLM |
| `POST /api/v1/explain` | Та же версия и тот же набор решений | Повторная проверка и расчёт на сервере, затем AI- или шаблонное объяснение |
| `GET /health/live` | Нет | Жив ли процесс API |
| `GET /health/ready` | Нет | Загружены ли корректные данные и готов ли расчётный API |
| `GET /health/ai` | Нет | Доступность Ollama и наличие настроенной локальной модели; не гарантия успешной генерации |

В этой редакции JSON-поля используют `snake_case`. Это изменение транспортного контракта относительно предыдущего TypeScript-проекта; автоматическая совместимость с прежними `camelCase`-полями не предполагается.

### 7.2. Минимальное сообщение сценария

```json
{
  "model_version": "tech2-v1",
  "selections": [
    { "measure_id": "M7", "district_id": "nura" },
    { "measure_id": "M8", "district_id": "nura" },
    { "measure_id": "M10", "district_id": "nura" },
    { "measure_id": "M12" },
    { "measure_id": "M5", "district_id": "saryarka" }
  ]
}
```

Для городской меры `district_id` отсутствует: `null`, строка `"город"` и лишние поля не принимаются. Цены, эффекты, бюджет, веса, prompt и готовый Score от клиента не поступают. Пример решений взят из Tech2; имена полей — наше проектное решение. [ТЗ-2, §§3–4]

### 7.3. Состав ответов

| Ответ | Основные поля |
|---|---|
| Проверка черновика | `model_version`, `valid_draft`, `can_evaluate`, `budget`, `errors` |
| Числовой отчёт | `model_version`, `scenario_key`, `selections`, `budget`, `baseline`, `after`, `score_delta`, `indicator_changes`, `measure_effects`, `synergy_effects` |
| Снимок `baseline` / `after` | Score, средний и минимальный районный балл, все районы с минимальным баллом, районные оценки, показатели и критические пары |
| Объяснение | `model_version`, `scenario_key`, `mode`, `llm_model`, `explanation`, `warning` |
| Тело объяснения | `summary`, `strengths`, `risks`, `recommendations` |
| Ошибка | Машинный `code`, понятный `message`, связанный путь поля или идентификаторы мер |

`validate` допускает от 0 до 5 полностью заполненных решений; все остальные ограничения уже проверяются. `can_evaluate=true` только для валидных пяти решений. При неизвестных ID не выдаём частичную сумму как точную стоимость: соответствующие значения бюджета остаются `null`.

Ключ `scenario_key` строит API из версии и набора, отсортированного по числовому ID мероприятия. Пример: `tech2-v1|M5@saryarka|M7@nura|M8@nura|M10@nura|M12@city`. Он связывает числовой отчёт и текст; не служит авторизацией или идентификатором сохранённой записи.

**Статусы:** `200` — успешная обработка, включая результат проверки черновика и явно отмеченный fallback; `409` — несовпадение версии симуляционной модели; `422` — некорректный ввод либо недопустимый окончательный сценарий; `413` — превышение лимита тела запроса; `500` — неожиданная ошибка. В неуспешных `evaluate` / `explain` числовой результат отсутствует, `score=null`. Health endpoints возвращают `503`, когда соответствующая проверка не пройдена.

Проектный лимит тела запроса — 16 КиБ. Его проверяет входной HTTP-слой по фактически полученным байтам, а не только по заголовку `Content-Length`. Содержимое ошибок не включает stack trace или внутренние настройки.

## 8. Поток одного пользовательского сценария

1. `ui` запрашивает `/catalog`, отображает исходное состояние и 14 мероприятий.
2. Добавление меры или смена района формирует кандидатный набор и вызывает `/validate`. UI принимает изменение только после успешной проверки; удаление решения доступно даже при временно недоступном API, но новый расчёт блокируется до проверки.
3. Кнопка расчёта отправляет неизменяемый снимок пяти решений в `/evaluate`. API проверяет его и возвращает отчёт без ожидания модели.
4. UI сохраняет отчёт в сессии и показывает его. Отдельная кнопка «Объяснить результат» отправляет тот же снимок в `/explain`; повторный запуск страницы сам по себе AI не вызывает.
5. API самостоятельно пересчитывает сценарий, собирает контекст, обращается к `llm`, проверяет структуру ответа и возвращает текст с тем же ключом сценария.
6. При любом изменении решений прежний отчёт и объяснение сбрасываются. Ответ сохраняется только при совпадении ключа со снимком, для которого он запрошен.

Две кнопки — выбранное упрощение UI, а не правило ТЗ. Оно отделяет задержку генерации от расчёта и исключает автоматическое повторение LLM-вызовов при перерисовках Streamlit. Очередь задач, брокер, фоновые workers и отдельный WebSocket API для этого потока не требуются.

## 9. AI-граница и поведение при отказах

`services/explanations.py` передаёт модели только серверный отчёт: выбранные меры, стоимость, лаги, эффекты, синергии, показатели до/после, критические пары и составляющие Score. Роль LLM в исходном ТЗ именно объяснительная. [ТЗ-2, §3, абзац «Роль ИИ»]

Адаптер использует Ollama `/api/chat` с `stream=false` и JSON Schema в `format`. Ответ повторно проверяется Pydantic-схемой. Эти возможности предусмотрены официальным API; схема ограничивает форму, но сама по себе не доказывает достоверность текста. Все числовые карточки UI заполняет из отчёта API, не из текста модели. [W9, W10]

В инструкции модели запрещены новые числовые прогнозы, изменение формулы и заявления об оптимальности набора. Рекомендации ограничиваются обсуждением следующего сценария в рамках каталога; улучшение альтернативы нельзя заявлять без отдельного расчёта. Реальные городские последствия не выдаются за подтверждённый прогноз синтетического симулятора. [АРХ-1, §8]

**Проектные лимиты:** один одновременно выполняемый AI-запрос в процессе API; при занятости — немедленное шаблонное объяснение с причиной `AI_BUSY`, без скрытой очереди. Для обращения к модели задаётся общий предел времени, например 45 секунд, а тайм-аут UI для `/explain` — больше него, например 55 секунд. Это настройки, не обещание фактической скорости. HTTP-вызов LLM асинхронный; он не должен блокировать обработку обычных расчётов.

| Ситуация | Поведение |
|---|---|
| Модель ещё загружается или отсутствует | Расчёт доступен; AI-блок сообщает о неготовности |
| Ollama недоступна, вернула ошибку или превышено время ожидания | `mode="fallback"`, предупреждение и объяснение из вычисленных данных |
| JSON неполный или не прошёл схему | Тот же fallback; повреждённый ответ не показывается как успешный AI-анализ |
| Другой AI-запрос уже выполняется | Fallback с причиной `AI_BUSY`; повтор возможен по явному действию пользователя |
| Получен корректный ответ модели | `mode="llm"`, сервер указывает реально использованную модель |
| API или датасет не готовы | Новые расчёты недоступны; UI не подставляет фиктивные результаты |

Fallback явно подписывается: **«AI недоступен: показано шаблонное объяснение»**. В нём `llm_model=null`. Сам по себе он не выполняет требование настоящего AI-анализа. Автоматического переключения на внешний облачный сервис в выбранной архитектуре нет. [ТЗ-1, раздел Must have; АРХ-1, §8.3]

## 10. Docker: сети, запуск и конфигурация

### 10.1. Сети и доступ

| Сеть | Подключённые сервисы | Назначение |
|---|---|---|
| `app_net` | `ui`, `api` | Интерфейс ↔ API |
| `llm_net` | `api`, `llm`, `model-init` | API ↔ локальная модель; подготовка модели |

Обе сети — обычные Compose bridge-сети. UI и Ollama не имеют общей сети. Флаг `internal: true` по умолчанию не ставим: первоначальная загрузка весов требует исходящего доступа из Ollama к реестру моделей. Отсутствие публикации порта не равно запрету исходящего интернета. [W2, W6]

Наружу опубликован только UI. Для доступа команды с других машин привязку UI нужно явно изменить и ограничить доступ на хосте. Для отладки допустима публикация API на `127.0.0.1:8000` через `compose.dev.yaml`; Ollama наружу не публикуем.

Это схема локального или закрытого демо, **не публичный защищённый сервис**. Авторизация и HTTPS-прокси в неё не входят. Серверные запросы из Streamlit не требуют открытия браузерного CORS-доступа к API; защиту самого Streamlit не отключаем.

### 10.2. Порядок запуска и проверки готовности

```text
api запускается независимо от llm
  └─ датасет корректен → /health/ready = 200 → запускается ui

llm запускается параллельно
  └─ сервер отвечает → запускается model-init
       └─ модель подготовлена и пробный запрос успешен → model-init завершается
```

Для `ui` используется зависимость от здорового `api`; для `model-init` — от здорового `llm`. Одного `depends_on` без проверки здоровья недостаточно, чтобы ждать готовности сервиса. `api` не зависит от успешного завершения `model-init`, иначе загрузка AI заблокирует весь симулятор. [W11]

| Компонент | Проверка | Что она не доказывает |
|---|---|---|
| `ui` | `/_stcore/health` | Что API или AI доступны |
| `api` | `/health/ready`: данные загружены и базовый расчёт подготовлен | Что локальная модель готова |
| `llm` | Успешный запрос списка моделей, например через штатный CLI `ollama list` | Что нужная модель присутствует и помещается в память |
| `model-init` | Наличие выбранной модели и успешный пробный запрос | Что любой будущий запрос завершится без ошибки |

Готовность AI отображается отдельно. `/health/ai` проверяет доступность сервера, наличие модели и ожидаемый digest, когда он задан, но не запускает генерацию при каждом опросе. [W1, W8]

Рабочие сервисы используют `restart: unless-stopped`; `model-init` — `restart: no`. Healthcheck помечает состояние, но сам по себе не гарантирует перезапуск зависшего контейнера; эта схема не включает отдельный автоматический «лечащий» сервис. [W12]

### 10.3. Образы и параметры

| Параметр | Где используется | Смысл |
|---|---|---|
| `API_BASE_URL` | `ui` | `http://api:8000` |
| `DATA_DIR` | `api` | `/app/data/tech2-v1` |
| `LLM_BASE_URL` | `api`, `model-init` | `http://llm:11434` |
| `LLM_MODEL` | `api`, `model-init` | Полный тег выбранной локальной модели; обязательный параметр AI-режима |
| `LLM_EXPECTED_DIGEST` | `api`, `model-init` | Ожидаемое содержимое весов; фиксируется после первичной проверки модели, несовпадение означает неготовность AI |
| `LLM_TIMEOUT_SECONDS` | `api` | Общий предел ожидания AI-анализа |
| `MODEL_INIT_TIMEOUT_SECONDS` | `model-init` | Отдельный предел подготовки весов, не равный тайм-ауту обычного AI-запроса |
| `OLLAMA_HOST` | `llm` | `0.0.0.0:11434` внутри контейнера |
| `OLLAMA_NO_CLOUD` | `llm` | `1`, отключение облачных функций |
| `LOG_LEVEL` | Python-контейнеры | Уровень технических логов |

Бюджет, горизонт, веса и ограничения не задаются через `.env`: их источник — версионированные правила. Значения окружения передаются сервисам явно через Compose; секретные или неиспользуемые параметры не раздаются всем контейнерам.

В рабочих образах фиксируются версии Python-образа и зависимостей; плавающий `latest` не используется. Для Ollama фиксируются образ и идентификатор весов: тег и фактический digest, который доступен в списке моделей. Совпадение тега без проверки содержимого не принимается за полную воспроизводимость. [W8]

При разработке исходники монтируются через `compose.dev.yaml`; в демонстрационной сборке используются копии кода из образов, без обязательных bind mounts. Python-процессы запускаются непривилегированным пользователем. Docker socket не монтируется; режим `privileged` не нужен. Веса не включаются в Git или Python-образы.

## 11. Уточнения, влияющие на архитектуру

| Вопрос | Принятое решение / ограничение |
|---|---|
| Нужно ли ровно по одной мере каждого направления? | Сохраняем рабочую трактовку предыдущей архитектуры: правила Tech2, то есть ровно 5 мер, не более 2 из направления. Формулировка Tech1 неоднозначна; считать противоречие официально разрешённым нельзя. При другом разъяснении меняются правило и тесты, не контейнерная схема. [ТЗ-1; ТЗ-2, §4; АРХ-1, §1.2] |
| Что означает название «на 5 часов»? | Таймер пятичасовой игры не закладываем. Расчётный горизонт Tech2 — 8 кварталов; срок разработки из запроса — 3 часа. [ТЗ-2, §2; АРХ-1, §1.1] |
| Почему нет БД? | В выбранном MVP нет постоянной истории и общего рейтинга; исходные данные статичны. Добавление хранения потребует явного расширения задачи. |
| Почему не один контейнер? | UI и API имеют разные процессы и зависимости; LLM — отдельный тяжёлый runtime. Разделение сохраняет один расчётный backend и изолирует его от процесса генерации. |
| Почему нет отдельного контейнера расчёта? | У него нет собственного хранения, сетевого протокола или независимого жизненного цикла. Вынос добавит интеграцию без нужной для данного MVP функции. |
| Какой AI-провайдер нужен? | В выбранной схеме внешнего провайдера нет: локальная модель в Ollama. Облачный API означал бы отдельное изменение архитектурного допущения, а не незаметный резервный путь. |
| Выбрана ли конкретная модель? | Нет: данные о доступной памяти, GPU и уже подготовленных весах не предоставлены. `LLM_MODEL` — обязательный параметр окружения; качество и скорость необходимо проверить на целевой машине. |
| Можно ли работать без интернета? | Рабочий сценарий не требует внешнего AI. Однако образы, Python-зависимости и веса должны быть заранее доступны локально; первичный запуск с пустыми кешами не объявляется автономным. |
| Что сохраняется при перезапуске? | Веса модели и файлы в образах; сценарии пользователей не сохраняются. |
| Можно ли менять Score через LLM или UI? | Нет: API берёт исходные данные сам, окончательно валидирует набор и рассчитывает результат одним движком. [ТЗ-2, §§3–4] |
| Гарантирует ли эта схема завершение за 3 часа? | Нет. Она ограничивает объём разработки, но готовность Docker, скачивание весов, ресурсы машины и знакомство команды со стеком остаются внешними условиями. |

**Итоговая граница ответственности:** `ui` собирает и показывает; `api` проверяет и считает; `llm` формулирует объяснение; `model-init` подготавливает модель. Исходные бизнес-данные принадлежат только API, пользовательский черновик — только сессии UI, веса — только тому Ollama.
