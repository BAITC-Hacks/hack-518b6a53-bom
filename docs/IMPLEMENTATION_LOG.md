# Журнал реализации

## Этап 1 — структура и контракты

- Добавлены пакеты `backend`, `backend/domain`, `backend/services`, `backend/adapters`, `shared` и каталог `backend/prompts`.
- Созданы неизменяемые доменные dataclasses, Pydantic v2 схемы HTTP, загрузка инфраструктурных настроек, пример окружения и исключения Git/Docker.
- Зафиксированы границы и сигнатуры будущих `load_dataset`, `validate_scenario`, `simulate`, `build_report`; публичные схемы catalog/validate/evaluate/explain/health описаны в `docs/BACKEND_CONTRACT.md`.
- Фактически выполненные проверки: чтение `data.md`, `ARCHITECTURE_PYTHON_DOCKER.md`, относящихся разделов `architechture.md`, промпта этапа и исходного `git status`/`git diff`; повторный просмотр созданных файлов и статуса рабочего дерева. Тесты, приложение и сборка не запускались.
- Ограничения: данные, загрузчик, валидатор, симулятор, HTTP-маршруты, OpenAI-клиент и Docker-упаковка относятся к следующим этапам. Схемы и доменные типы в этом этапе не подтверждены исполнением.

### Уточнение этапа 1 — сериализация городского решения

- `SelectionSchema` опускает отсутствующий `district_id` при собственной Pydantic-сериализации, в том числе внутри списков решений. Входной явный `null` по-прежнему отвергается.
- Контракт уточнён для вложенных решений; остальные схемы и будущие этапы не менялись.
- Проверка: просмотр изменённых схемы, контракта и рабочего дерева. Тесты и приложение не запускались.

## Этап 2 — версионированные данные и загрузчик

- Добавлены `data/tech2-v1/districts.json`, `measures.json`, `rules.json`, `presets.json`: исходные показатели пяти районов, 14 мер, веса, бюджет, ограничения, три конфликта, три синергии и два набора решений. Районные оценки и готовые результаты в данных не хранятся. Для второго набора использованы районные привязки из задания этапа.
- Добавлен `backend/adapters/dataset.py`: читает четыре JSON-файла, проверяет структуру, версии, ID, ссылки, диапазоны, суммы, правила конфликтов и синергий, а также корректность пресетов. При ошибке вызывает `ValueError` с именем файла и причиной; частичный `Dataset` не возвращается.
- Публичный интерфейс этапа: `load_dataset(path: str | Path) -> Dataset`.
- Фактически выполненные проверки: прочитаны исходные документы, модели, `git diff` и `git status`; после записи просмотрены код загрузчика, правила и пресеты; выполнен `git diff --check` (новые неотслеживаемые файлы эта команда не проверяет). Тесты, загрузчик и приложение не запускались.
- Ограничения: числовой расчёт, HTTP и внешняя интеграция относятся к следующим этапам. Корректность загрузки и значений требует независимой проверки чтением.

## Этап 3 — проверка сценария

- Добавлен `backend/domain/validation.py`: проверяет черновой и окончательный наборы, ID мер и районов, привязку района к типу меры, число решений, повторы, бюджет, лимит направления и конфликты из `Dataset`. Собирает независимо определимые ошибки; при неизвестной мере не показывает частичную стоимость.
- Публичный интерфейс: `validate_scenario(dataset: Dataset, selections: tuple[Selection, ...], *, final: bool) -> ValidationResult`. Результат содержит `valid_draft`, `can_evaluate`, `budget` и ошибки с кодами из `docs/BACKEND_CONTRACT.md`.
- Фактически выполненные проверки: прочитаны требования, существующие модели, правила в версионированных данных, `git status` и `git diff`; после изменения выполнен просмотр diff и `git diff --check`. Тесты и приложение не запускались.
- Ограничения: проверка не рассчитывает Score; исполнение валидатора не проверялось. Числовой расчёт и HTTP-маршруты относятся к следующим этапам.
