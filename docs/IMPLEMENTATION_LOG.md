# Журнал реализации

## Этап 1 — структура и контракты

- Добавлены пакеты `backend`, `backend/domain`, `backend/services`, `backend/adapters`, `shared` и каталог `backend/prompts`.
- Созданы неизменяемые доменные dataclasses, Pydantic v2 схемы HTTP, загрузка инфраструктурных настроек, пример окружения и исключения Git/Docker.
- Зафиксированы границы и сигнатуры будущих `load_dataset`, `validate_scenario`, `simulate`, `build_report`; публичные схемы catalog/validate/evaluate/explain/health описаны в `docs/BACKEND_CONTRACT.md`.
- Фактически выполненные проверки: чтение `data.md`, `ARCHITECTURE_PYTHON_DOCKER.md`, относящихся разделов `architechture.md`, промпта этапа и исходного `git status`/`git diff`; повторный просмотр созданных файлов и статуса рабочего дерева. Тесты, приложение и сборка не запускались.
- Ограничения: данные, загрузчик, валидатор, симулятор, HTTP-маршруты, OpenAI-клиент и Docker-упаковка относятся к следующим этапам. Схемы и доменные типы в этом этапе не подтверждены исполнением.

### Уточнение этапа 1 — сериализация городского решения

- `SelectionSchema` опускает отсутствующий `district_id` при собственной Pydantic-сериализации, в том числе внутри списков решений. Входной явный `null` по-прежнему отвергается.
- Контракт уточнён для вложенных решений; остальные схемы и будущие этапы не менялись.
- Проверка: просмотр изменённых схемы, контракта и рабочего дерева. Тесты и приложение не запускались.

## Этап 2 — версионированные данные и загрузчик

- Добавлены `data/tech2-v1/districts.json`, `measures.json`, `rules.json`, `presets.json`: исходные показатели пяти районов, 14 мер, веса, бюджет, ограничения, три конфликта, три синергии и два набора решений. Районные оценки и готовые результаты в данных не хранятся. Для второго набора использованы районные привязки из задания этапа.
- Добавлен `backend/adapters/dataset.py`: читает четыре JSON-файла, проверяет структуру, версии, ID, ссылки, диапазоны, суммы, правила конфликтов и синергий, а также корректность пресетов. При ошибке вызывает `ValueError` с именем файла и причиной; частичный `Dataset` не возвращается.
- Публичный интерфейс этапа: `load_dataset(path: str | Path) -> Dataset`.
- Фактически выполненные проверки: прочитаны исходные документы, модели, `git diff` и `git status`; после записи просмотрены код загрузчика, правила и пресеты; выполнен `git diff --check` (новые неотслеживаемые файлы эта команда не проверяет). Тесты, загрузчик и приложение не запускались.
- Ограничения: числовой расчёт, HTTP и внешняя интеграция относятся к следующим этапам. Корректность загрузки и значений требует независимой проверки чтением.

## Этап 3 — проверка сценария

- Добавлен `backend/domain/validation.py`: проверяет черновой и окончательный наборы, ID мер и районов, привязку района к типу меры, число решений, повторы, бюджет, лимит направления и конфликты из `Dataset`. Собирает независимо определимые ошибки; при неизвестной мере или районе не показывает частичную стоимость.
- Публичный интерфейс: `validate_scenario(dataset: Dataset, selections: tuple[Selection, ...], *, final: bool) -> ValidationResult`. Результат содержит `valid_draft`, `can_evaluate`, `budget` и ошибки с кодами из `docs/BACKEND_CONTRACT.md`.
- Фактически выполненные проверки: прочитаны требования, существующие модели, правила в версионированных данных, `git status` и `git diff`; после изменения выполнен просмотр diff и `git diff --check`. Тесты и приложение не запускались.
- Ограничения: проверка не рассчитывает Score; исполнение валидатора не проверялось. Числовой расчёт и HTTP-маршруты относятся к следующим этапам.

## Этап 4 — числовое ядро и отчёт

- Добавлены `backend/domain/simulation.py` и `backend/domain/report.py`. Симуляция начинает с исходных показателей, сортирует меры по числовому ID, применяет эффекты с лагом и отдельные фиксированные синергии, один раз ограничивает показатели, рассчитывает районные оценки, среднюю, минимум, критические пары и Score по правилам датасета. Пустой набор допускается только для внутренней базы; непустой набор проверяется как окончательный сценарий.
- Отчёт содержит канонические решения и ключ сценария, бюджет, базовый и итоговый снимки, прирост Score, фактические изменения всех пар «район × показатель», вклады мер до ограничения и синергии отдельно.
- Публичные интерфейсы: `simulate(dataset: Dataset, selections: tuple[Selection, ...]) -> SimulationResult`, `build_report(dataset: Dataset, selections: tuple[Selection, ...], simulation: SimulationResult, baseline: SimulationResult) -> ScenarioReport`; вспомогательная функция `canonical_selections(selections)` задаёт общий порядок для расчёта и отчёта.
- Фактически выполненные проверки: прочитаны требования, исходные данные, существующие модели и валидатор, исходный `git status`/`git diff`; после записи код просмотрен чтением и выполнен `git diff --check`. Тесты, симуляция, загрузчик и приложение не запускались, числовые ориентиры исполнением не сверялись.
- Ограничения: согласованность переданных в `build_report` результатов симуляции и базы с указанными решениями обеспечивается вызывающим кодом. HTTP и интеграция с OpenAI относятся к следующим этапам.

## Этап 5 — HTTP API сценариев

- Добавлены `backend/main.py`, `backend/routes.py`, `backend/services/scenarios.py`. При старте загружается полный Dataset и рассчитывается baseline; готовый сервис помещается в состояние приложения только после обоих успешных шагов. При ошибке инициализации live остаётся доступным, ready и прикладные маршруты отвечают 503.
- Реализованы каталог, проверка черновика и окончательный расчёт, единая форма ошибок, проверка версии модели и ограничение тела в 16 КиБ по фактически полученным байтам до обработки маршрута. Валидация и расчёт сценария собраны в сервисе для повторного использования будущим explain.
- Уточнено преобразование доменного `Selection` в HTTP: вложенные решения пресетов каталога и ответа evaluate передаются в `SelectionSchema` без `district_id` для городской меры и со строковым `district_id` для районной. Прочие nullable поля, включая `MeasureEffect.district_id`, сохраняют свою форму.
- Публичные интерфейсы: ASGI-приложение `backend.main:app`; `ScenarioService.validate_draft(model_version, selections)` и `ScenarioService.evaluate(model_version, selections)`; маршруты `GET /api/v1/catalog`, `POST /api/v1/validate`, `POST /api/v1/evaluate`, `GET /health/live`, `GET /health/ready`.
- Фактически выполненные проверки: чтение требований, существующего кода и исходного `git diff`; просмотр изменённых файлов и `git diff --check`. После уточнения преобразования повторно сопоставлены `SelectionSchema`, контракт и diff; выполнен `git diff --check`. Тесты и приложение не запускались.
- Ограничения: OpenAI и explain относятся к следующим этапам; API не проверен исполнением. Для локального запуска вне контейнера требуется указать `DATA_DIR`, поскольку значение по умолчанию — `/app/data/tech2-v1`.

## Этап 6 — факты и шаблонное объяснение

- Добавлены `backend/services/explanations.py`, `backend/adapters/fallback.py` и `backend/prompts/explanation.txt`. Сервис вызывает окончательную проверку и расчёт через `ScenarioService.evaluate`, строит из серверного отчёта контекст для объяснения и передаёт его асинхронному адаптеру. Контекст содержит выбранные меры и каталог, стоимость, лаги, эффекты до clip, синергии, показатели и Score до/после, критические пары и составляющие формулы.
- Шаблонное объяснение строится из отчёта; fallback явно помечен `mode=fallback`, `llm_model=null` и предупреждением с типизированной причиной. Ответ адаптера перед выдачей повторно проверяется по `ExplanationSchema` и непустому ID реально использованной модели.
- Публичные интерфейсы: `ExplanationService.explain(model_version, selections) -> ExplainResponse`, `ExplanationAdapter.explain(facts) -> ExplanationSuccess | ExplanationFailure`, `build_ai_context(report, dataset)`, `template_explanation(facts)` и `fallback_response(facts, reason)`. Причины отказа заданы `ExplanationFailureReason`.
- Фактически выполненные проверки: чтение требований, существующего кода, `git status` и `git diff`; просмотр изменённых файлов и diff. Тесты, приложение и внешний API не запускались.
- Ограничения: адаптер OpenAI и HTTP-маршрут explain относятся к этапу 7. Проверка схемы ответа не доказывает фактическую верность свободного текста модели; реальный AI-ответ на этом этапе не получен.

## Этап 7 — OpenAI и маршруты объяснения

- Добавлен `backend/adapters/llm.py`: асинхронный Responses API со структурированным `ExplanationSchema`, `store=false`, без инструментов и streaming; общий тайм-аут, отключённые повторы SDK, атомарное занятие одного AI-слота и fallback при ошибках провайдера или ответа, включая повреждённые поля объекта ответа. Слот освобождается при ошибке и отмене. Провайдерский ответ и исключения не выдаются клиенту. Числа поступают только из серверного отчёта.
- Клиент `AsyncOpenAI` создаётся при старте приложения с официальным endpoint и закрывается в lifespan. Добавлены `POST /api/v1/explain` и локальный `GET /health/ai`; explain использует прежние проверку и расчёт, сохраняет 409/422 для неверного ввода и возвращает HTTP 200 с явным fallback при отказе AI. Health не делает внешнего запроса.
- Публичные интерфейсы: `OpenAIExplanationAdapter(settings, client).explain(facts)`, `.health()`, `POST /api/v1/explain`, `GET /health/ai`. Настройки: `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_TIMEOUT_SECONDS=45`, `OPENAI_MAX_OUTPUT_TOKENS=2000`.
- Для этапа 8: выбрать и закрепить `openai==3.17.0` (официальный релиз от 22 сентября 2026 года). Сверен документированный Python-интерфейс `responses.parse(..., text_format=PydanticModel)` и `output_parsed` по официальному руководству OpenAI; локально пакет `openai` не установлен, поэтому фактическая версия SDK отсутствует. Зависимость в этом этапе не добавлялась.
- Фактически выполненные проверки: чтение требований и текущего кода, `git status` и `git diff`; сверка интерфейса с официальной документацией OpenAI и страницы релизов SDK; проверка отсутствия установленного пакета через `pip show`; просмотр итогового diff и `git diff --check` (не охватывает новый неотслеживаемый файл). Тесты, приложение и платные API-запросы не запускались.
- Ограничения: исполнение интеграции не проверено; установку и закрепление зависимостей выполняет этап 8. Схема ответа ограничивает форму, но не доказывает достоверность текста модели. `/health/ai` сообщает только состояние текущего процесса, а не текущую доступность OpenAI.

## Этап 8 — упаковка бэкэнда MVP

- Добавлены `docker/api.Dockerfile`, `compose.yaml`, `compose.dev.yaml`, `requirements/api.in` и созданный `uv pip compile` файл `requirements/api.lock` с 19 разрешёнными версиями для Python 3.12. Образ содержит код и датасет; процесс работает от непривилегированного пользователя. Compose содержит только `api`, публикует `127.0.0.1:8000`, явно передаёт настройки и проверяет `/health/ready` без OpenAI. Bind mounts есть только в dev-конфигурации.
- Обновлены `.env.example`, `.dockerignore` и `README.md`: настройка ключа и модели, запуск и остановка, Swagger, curl-примеры первого пресета Tech2, различие расчёта, AI и fallback, health и ручная демонстрация.
- Публичные интерфейсы этапа: Docker-образ с `backend.main:app` и одним Uvicorn worker; Compose-сервис `api`; переменные `LOG_LEVEL`, `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_TIMEOUT_SECONDS`, `OPENAI_MAX_OUTPUT_TOKENS` и заданный в Compose `DATA_DIR`. HTTP-контракт предыдущих этапов не менялся.
- Фактически выполненные проверки: прочитаны код, исходный `git diff`, журнал и документы требований; `uv pip compile` успешно разрешил lock для Python 3.12; `docker compose --env-file .env.example -f compose.yaml -f compose.dev.yaml config --quiet` завершился без ошибок; выполнен просмотр файлов и `git diff --check`. Приложение, тесты, Docker-сборка, контейнер и платные OpenAI-запросы не запускались.
- Ограничения: сборка и работа образа, HTTP-маршруты и интеграция с OpenAI не проверены исполнением. Для настоящего AI нужны действующие ключ и ID доступной модели, а также исходящий сетевой доступ. Качество объяснений модели требует отдельной оценки.

## Проверка и исправления после этапа 8 — 2026-09-23

Текущий запрос пользователя разрешил исправления и живые проверки, которые не выполнялись на этапах первоначальной реализации. Постоянный тестовый набор в репозиторий не добавлен; диагностические скрипты находятся в `/tmp/bom-backend-audit/`.

Исправлены три дефекта:

- `backend/domain/validation.py`: неизвестный район больше не скрывает стоимость известных мер. Для первого пресета с ошибочным районом возвращаются `spent=95`, `remaining=5` и `UNKNOWN_DISTRICT`. Только неизвестная мера делает стоимость неопределённой. Исправлено противоречие контракта исходному промпту этапа 3.
- `backend/main.py`: обработчик HTTP-ошибок регистрируется для базового исключения Starlette, поэтому ошибки маршрутизации 404/405 имеют общий формат `errors`/`score=null`. Заголовки исключения, в том числе `Allow`, сохраняются.
- `backend/settings.py`, `backend/main.py`: `LOG_LEVEL` нормализуется, проверяется и применяется к логам приложения и Uvicorn при старте lifespan.

Публичные маршруты и схемы не изменены. Обновлены контракт и README.

Фактически выполнено:

- Сверены данные Tech2, модели, загрузчик, валидация, расчёты, сервисы, маршруты, fallback, AI-адаптер, настройки и упаковка.
- `docker compose -p bom-audit build api`: образ успешно собран из существующего lock-файла. Python 3.12.14, OpenAI SDK 3.17.0. Временный контейнер опубликован на `127.0.0.1:32768`; штатный healthcheck вернул `healthy`.
- `python /tmp/bom-backend-audit/live.py`: прошли 36 настоящих HTTP-запросов к опубликованному порту. Проверены live/ready/ai, каталог, validate/evaluate/explain, оба пресета, fallback без конфигурации, неизвестные ID и версия, явный null и лишние поля, повреждённый JSON, пустой окончательный набор, бюджет 105, ошибки 404/405, OpenAPI/Swagger. Проверены тела ровно 16384 и 16385 байт, в том числе chunked без Content-Length.
- `domain.py` выполнен внутри контейнера: база `average=56.8624`, `minimum=49.18`, две критические пары, `Score=52.55768`; первый пресет `spent=95`, `Score=56.54307`; второй `spent=61`, `Score=55.343025`. Прошли все 240 перестановок обоих пресетов, повторные расчёты, ограничения, конфликты, бюджет, лаги, все синергии, clip после суммы, граница 40 и защита данных от изменения. Загрузчик отклонил 10 вариантов повреждённых данных.
- `async_checks.py` выполнен внутри контейнера: настоящий SDK сериализовал запрос и разобрал структурированный ответ через локальный MockTransport; проверены `store=false`, строгая схема, модель из ответа и отсутствие повторов. Проверены fallback при 401/429/500, сетевой ошибке, тайм-ауте, отказе, неполном/пустом/невалидном ответе; отсутствие утечки сообщения провайдера, AI_BUSY без изменения статуса, отмена и повторное занятие слота. Через ASGI проверены доступность evaluate во время explain, режим llm с подменённым клиентом, неготовый датасет и уровни логгеров. Ошибки расчётного кода не маскируются под fallback. Middleware прекращает чтение при превышении лимита.
- Интерфейс SDK сопоставлен с установленной сигнатурой и [официальной документацией Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Ограничение: реальный платный вызов OpenAI не выполнен — отсутствуют OPENAI_API_KEY, OPENAI_MODEL и файл .env. Успешный ответ с подменённым транспортом не подтверждает доступность провайдера или качество настоящего объяснения.

После проверки временный контейнер `bom-audit-live` остановлен и удалён, сеть `bom-audit_default` удалена. Собранный образ оставлен в локальном Docker. `git diff --check` прошёл; коммиты и push не выполнялись.
