# Промпты для разработки бэкэнда MVP

## Как использовать

Запускайте этапы 1–8 последовательно в отдельных агентах gpt-sol в одном репозитории. Каждому реализующему агенту передайте **общую инструкцию и полный промпт его этапа**. После каждого этапа запускайте нового агента с промптом проверяющего. При FAIL передайте замечания реализующему агенту и повторите проверку. Переходите дальше после PASS.

Результат этой последовательности — бэкэнд, а не интерфейс: FastAPI, статические данные, расчётное ядро, OpenAI и Docker. Модель приложения задаётся отдельно через OPENAI_MODEL.

Проверяющий только читает код. Он не создаёт и не запускает тесты, не запускает приложение. Его PASS означает отсутствие найденных нарушений при статическом анализе, а не подтверждённую работоспособность. Команды ручного запуска будут описаны в README на этапе 8.

## Общая инструкция реализующему агенту

```text
Ты реализуешь один этап бэкэнда MVP «Аким на 5 часов».

Работай в текущем репозитории. Сначала прочитай существующий код,
git diff и документы своего этапа. Не считай, что результаты предыдущих
агентов обязательно правильные или что файлы уже существуют.

Источники требований:
1. Этот промпт и явно зафиксированные уточнения пользователя.
2. data.md, раздел Tech2 — исходные данные, формула и бизнес-правила.
3. ARCHITECTURE_PYTHON_DOCKER.md — структура и поведение системы.
4. docs/BACKEND_CONTRACT.md — согласованные детали реализации,
   которые не должны противоречить пунктам выше.

Поправки пользователя к архитектуре:
- Реализуем только бэкэнд MVP.
- Вместо Ollama используем внешний OpenAI API.
- Модель приложения задаётся через OPENAI_MODEL.
- gpt-sol — модель агента разработки; её имя нельзя автоматически
  использовать как model ID приложения.
- Ollama, model-init, веса модели и llm_net не нужны.
- Не создавай frontend, БД, авторизацию, историю, очереди, RAG
  и агентов внутри приложения.
- Не создавай и не запускай тесты. Отдельный агент проверит код чтением.

Обязательные принципы:
- Числа рассчитывает только Python-ядро; OpenAI объясняет результат.
- domain зависит только от стандартной библиотеки Python.
- Бизнес-константы берутся из версионированных данных.
- Не выдумывай исходные данные, зависимости, API SDK или результаты проверок.
- Не округляй промежуточные расчёты.
- Не переписывай чужие изменения и не выполняй git reset/clean.
- Не делай коммиты и push.
- Не читай и не показывай содержимое настоящего .env или API-ключи.
- Не оставляй заглушки вместо функциональности своего этапа.
- Не реализуй будущие этапы.
- При противоречии, которое нельзя разрешить по указанным источникам,
  сообщи конкретную проблему вместо самостоятельного изменения требований.

Перед изменениями кратко перечисли затрагиваемые части.
После работы добавь запись в docs/IMPLEMENTATION_LOG.md:
номер этапа, сделанные изменения, публичные интерфейсы,
фактически выполненные проверки и известные ограничения.
Этот журнал — передача контекста, а не доказательство корректности.

В финальном ответе перечисли результат, изменённые файлы,
ограничения и что должен проверить проверяющий.
Не заявляй, что код запускался или проверки прошли, если этого не было.
```

## Этап 1. Структура проекта и единые контракты

```text
Создай первоначальную структуру бэкэнда и зафиксируй контракты,
на которые будут опираться следующие агенты.

Прочитай data.md и ARCHITECTURE_PYTHON_DOCKER.md полностью.

Создай пакеты backend, backend/domain, backend/services,
backend/adapters, shared; каталог backend/prompts.
Добавь необходимые __init__.py.

Создай docs/BACKEND_CONTRACT.md:
- границы MVP и приоритет источников;
- замену локальной модели на OpenAI;
- перечень этапов и владельцев модулей;
- точные доменные структуры и сигнатуры функций;
- точные HTTP-схемы, ошибки и правила сериализации;
- инфраструктурные переменные и поведение при отсутствии OpenAI.

Определи доменные структуры в backend/domain/models.py:
район, мероприятие, правила, датасет, выбранная мера,
ошибка валидации, бюджет, результат валидации, снимок расчёта,
эффекты меры и синергии, итоговый отчёт.

Используй dataclasses и стандартные типы.
Загруженные данные должны быть защищены от изменения,
включая вложенные коллекции.

Зафиксируй интерфейсы:
- load_dataset(path) -> Dataset;
- validate_scenario(dataset, selections, final=...) -> ValidationResult;
- simulate(dataset, selections) -> SimulationResult;
- build_report(dataset, selections, simulation, baseline) -> ScenarioReport.
Публичные HTTP-сервисы всегда валидируют сценарий до simulate.
Пустой набор разрешён simulate только как внутренний базовый расчёт.
На этом этапе документируй будущие функции, не создавай их заглушки.

Реализуй Pydantic v2 схемы в shared/schemas.py.
Поля snake_case; неизвестные поля запрещены.
В запросе только model_version и selections.
В решении только measure_id и необязательный district_id.
Отсутствующий district_id допустим на транспортном уровне;
явный null недопустим. Соответствие типу меры проверяет ядро.

Зафиксируй ответы из §7 архитектуры:
catalog, validate, evaluate, explain и health.
Для baseline/after используй одинаковый Snapshot:
score, average, minimum, weakest_district_ids,
districts, critical_pairs.
Budget: limit, spent, remaining.
Explanation: summary — строка;
strengths, risks, recommendations — списки строк.
Ответ explain: model_version, scenario_key, mode,
llm_model, explanation, warning.
mode: llm или fallback.
warning: null либо объект code/message.
Единый ответ ошибки: errors — список code/message/path,
score — null.
Успешный validate не содержит Score.

Зафиксируй ID районов:
yesil, almaty, saryarka, baikonur, nura.
Индикаторы сохраняют ID T1…C2; меры — M1…M14.

Создай backend/settings.py для DATA_DIR, LOG_LEVEL,
OPENAI_API_KEY, OPENAI_MODEL, OPENAI_TIMEOUT_SECONDS,
OPENAI_MAX_OUTPUT_TOKENS.
Значения по умолчанию: /app/data/tech2-v1, INFO, 45 секунд,
2000 выходных токенов. Ключ и модель по умолчанию отсутствуют.
Отсутствие AI-конфигурации не блокирует калькулятор.

Создай .env.example без секретов, .gitignore и .dockerignore.
Dockerfile и Compose будут реализованы на этапе 8.

Не пиши алгоритмы, маршруты и OpenAI-клиент.
Не добавляй фиктивные работающие обработчики.
```

## Этап 3. Валидация сценариев

```text
Реализуй backend/domain/validation.py по общему контракту.

Два режима:
- черновик: от 0 до 5 полностью заполненных решений;
- окончательный сценарий: ровно 5 решений.

Проверяй:
- известные ID мероприятий и районов;
- отсутствие повторных мероприятий;
- обязательный район для районной меры;
- отсутствие района для городской меры;
- стоимость не выше 100;
- не более двух мероприятий одного направления;
- M1/M3 несовместимы независимо от районов;
- M4/M7 несовместимы только в одном районе;
- M5/M13 несовместимы только в одном районе.

Правила и цены бери из Dataset.
Собирай все независимо определимые ошибки,
не падай при неизвестных ID.

valid_draft означает выполнение правил черновика.
can_evaluate=true только для допустимых пяти решений.
Для окончательного режима нехватка решений — ошибка.

Если есть неизвестная мера, spent и remaining равны null.
limit остаётся известным.
Если все меры известны, показывай стоимость перечисленного набора,
даже когда набор недопустим; каждая запись учитывается один раз.
Городская мера не умножается на число районов.

Не вычисляй Score и не изменяй входные данные.
Коды ошибок должны быть стабильными и описанными в контракте.
```

## Этап 4. Расчётное ядро и отчёт

```text
Реализуй backend/domain/simulation.py и report.py.

Каждый расчёт начинается с исходного датасета.
Канонически сортируй решения по числовой части measure_id.

Порядок вычислений:
1. Эффект мероприятия умножается на (H - lag) / H.
2. Районная мера влияет на выбранный район; городская — на все.
3. Фиксированные синергии применяются отдельно, без масштабирования:
   M1/M2: T1 +2 в районе M1;
   M10/M12: B1 +2 в районе M10;
   M5/M6: E2 +2 в районе M5.
4. Суммируются все эффекты и синергии.
5. Единственный clip каждого показателя в [0, 100].
6. Районные оценки по весам.
7. Средняя оценка по долям населения.
8. Минимальная районная оценка и все районы с этим минимумом.
9. Критические пары со значением строго <40.
10. Score = 0.7 * average + 0.3 * minimum - число критических пар.

Все коэффициенты и синергии бери из данных, не дублируй константы.
Не округляй промежуточные значения и не ограничивай сам Score
диапазоном показателей.
Для сравнения равных минимумов используй абсолютный допуск 1e-8.

Отчёт содержит baseline, after, score_delta, бюджет,
канонические selections, indicator_changes,
measure_effects и synergy_effects.
Вклады мер отражают эффекты после лага, но до clip.
Фактические итоговые изменения и синергии показывай отдельно.
Не назначай каждой мере независимый вклад в Score.

scenario_key:
tech2-v1|M5@saryarka|M7@nura|M8@nura|M10@nura|M12@city.
Порядок исходных selections не влияет на ключ и расчёт.

Ориентиры для анализа кода:
- база: average=56.8624, minimum=49.18,
  две критические пары, Score=52.55768;
- первый пресет: стоимость 95, average=58.0776,
  minimum=52.9625, критических пар 0,
  Score=56.54307, прирост=3.98539.

Эти значения не должны становиться константами реализации.
При расхождении проверь исходные данные и формулу.
```

## Этап 5. FastAPI и расчётные маршруты

```text
Реализуй backend/main.py, routes.py и services/scenarios.py.

В lifespan:
- загрузи и проверь Dataset;
- вычисли baseline;
- сохрани готовые зависимости в состоянии приложения.
При ошибке датасета сохрани состояние неготовности:
live работает, ready и прикладные маршруты возвращают 503.
Не обслуживай запросы с частичным датасетом.

Реализуй:
GET /api/v1/catalog
POST /api/v1/validate
POST /api/v1/evaluate
GET /health/live
GET /health/ready

catalog возвращает версию, районы, каталог, публичные правила,
baseline и пресеты.
validate проверяет черновик, не рассчитывает Score.
evaluate окончательно валидирует сценарий и строит отчёт.

Сервис сценариев должен быть повторно используемым будущим explain.
Не дублируй правила в маршрутах и Pydantic-схемах.

Статусы:
- 200: успешный запрос и результат бизнес-проверки черновика;
- 409: неизвестная model_version;
- 422: неправильная структура или недопустимый окончательный набор;
- 413: тело больше 16 КиБ;
- 503: датасет не готов;
- 500: неожиданная внутренняя ошибка.

Ошибки приведи к общей схеме, без stack trace и настроек.
Для неуспешного evaluate не возвращай числовой отчёт; score=null.

Проверяй лимит тела по реально полученным байтам,
включая запросы без Content-Length и потоковую передачу.
Не считывай неограниченное тело целиком перед проверкой лимита.

Не вызывай OpenAI, не добавляй CORS без потребности интерфейса.
Не создавай фиктивные explain и health/ai.
```

## Этап 6. AI-контекст и шаблонное объяснение

```text
Реализуй backend/services/explanations.py,
backend/adapters/fallback.py и backend/prompts/explanation.txt.

Подготовь поток объяснения:
окончательная валидация → серверный расчёт →
формирование фактов → адаптер объяснения.

Используй сервис сценариев этапа 5.
Не принимай от клиента готовые числа, отчёт или prompt.

Зафиксируй узкий асинхронный интерфейс адаптера:
получить серверные факты и вернуть проверенное Explanation
с идентификатором реально использованной модели
либо типизированную причину отказа.
Внешний OpenAI-клиент будет добавлен следующим этапом.

В AI-контекст включи:
решения, стоимость, лаги, эффекты до clip, синергии,
показатели до/после, критические пары, части Score
и разрешённый каталог для рекомендаций.

Инструкция модели:
- отвечать по-русски в заданной структуре;
- объяснять только переданные факты;
- не пересчитывать и не придумывать числа;
- не менять правила;
- не заявлять оптимальность сценария;
- не обещать улучшение от альтернативы без её расчёта;
- отличать результаты синтетической модели от реального прогноза.

Шаблонное объяснение строится детерминированно из отчёта.
Покажи результат, сильные стороны, оставшиеся проблемы
и осторожные рекомендации без нового расчёта.
Не выдумывай риски, которых не следует из данных.

Fallback возвращает mode=fallback, llm_model=null,
warning с причиной и сообщением:
«AI недоступен: показано шаблонное объяснение».

Не подключай сеть и не выдавай шаблон за настоящий AI.
```

## Этап 7. OpenAI API и маршрут объяснения

```text
Реализуй backend/adapters/llm.py и подключи его к сервису объяснений.

Перед реализацией сверь точный интерфейс выбранной версии
официального Python SDK с официальной документацией OpenAI:
https://developers.openai.com/api/docs/guides/structured-outputs
Если SDK уже установлен, проверь также его фактическую версию.
Зафиксируй использованную версию в журнале для этапа упаковки.

Используй AsyncOpenAI, Responses API и структурированный ответ
по Pydantic-схеме Explanation.
Не выдумывай методы SDK и model ID.

Конфигурация:
OPENAI_API_KEY, OPENAI_MODEL,
OPENAI_TIMEOUT_SECONDS=45,
OPENAI_MAX_OUTPUT_TOKENS=2000.
Используй официальный endpoint OpenAI.
Клиент создаётся и закрывается в lifespan.
Ключ доступен только серверу.

Передавай store=false.
Не используй инструменты, поиск, файлы, память диалога и streaming.
Отключи автоматические повторы SDK для предсказуемого времени ответа.
Весь внешний вызов ограничь общим тайм-аутом.

Разрешён один активный AI-запрос на процесс.
Проверка занятости и занятие слота должны быть атомарны
относительно других async-запросов.
При занятом слоте сразу fallback с AI_BUSY, без очереди.
Освобождай слот при успехе, ошибке и отмене.
Обычные расчёты не должны блокироваться AI-запросом.

Обрабатывай через fallback:
отсутствие конфигурации, ошибку авторизации, rate limit,
сетевую ошибку, тайм-аут, отказ модели, незавершённый ответ,
пустой результат и нарушение схемы.
Не возвращай сырые ответы провайдера или секреты.
Ошибки самого расчётного кода не маскируй под отказ AI.

Добавь POST /api/v1/explain:
сначала тот же расчёт и валидация, затем AI.
Успех AI: mode=llm и фактическая модель из ответа.
Отказ AI: HTTP 200 с явно отмеченным fallback.
Ошибки входных данных сохраняют 409/422 и не вызывают OpenAI.

Добавь GET /health/ai без внешних запросов:
configured, model, last_status, last_checked_at.
Начальное last_status=not_checked.
200: конфигурация есть и состояние not_checked либо ok.
503: конфигурации нет или последний вызов завершился ошибкой.
AI_BUSY не меняет состояние провайдера.
Документируй: это локальный статус конфигурации и последнего вызова,
он не подтверждает текущую доступность OpenAI.

Не выполняй платные запросы в рамках этого этапа.
```

## Этап 8. Docker и инструкция запуска

```text
Заверши упаковку готового бэкэнда MVP.

Прочитай реализацию всех предыдущих этапов и журнал.
Создай:
- docker/api.Dockerfile;
- compose.yaml;
- compose.dev.yaml;
- requirements/api.in и requirements/api.lock;
- актуальные .env.example, .dockerignore и README.md.

Python 3.12, один Uvicorn worker, backend.main:app.
Рабочий процесс — непривилегированный пользователь.
Контекст сборки — корень репозитория.
Датасет и код копируются в образ, bind mounts нужны только dev-режиму.
Healthcheck обращается к /health/ready и не зависит от OpenAI.

Compose содержит только api.
Публикуй API на 127.0.0.1:8000 для локального демо и Swagger.
Не добавляй несуществующий UI, Ollama, model-init, llm_net,
тома весов, БД или Docker socket.
API должен иметь исходящий доступ к OpenAI.

Передавай переменные явно. Не копируй .env в образ.
Фиксируй реально разрешённые версии зависимостей.
Lock-файл создавай инструментом разрешения зависимостей,
не выдумывай транзитивные версии и хеши.
Если окружение не позволяет его получить, укажи блокер,
не представляй незавершённую упаковку как готовую.

README должен содержать:
- краткую архитектуру и границы MVP;
- настройку OPENAI_API_KEY и OPENAI_MODEL;
- команды сборки, запуска, остановки и просмотра логов;
- адрес Swagger;
- примеры curl для catalog, validate, evaluate и explain;
- различие рабочего калькулятора, настоящего AI и fallback;
- отсутствие сохранения сценариев;
- значение health endpoints;
- ручной сценарий демонстрации.

В примере evaluate/explain используй первый пресет Tech2.
В ручном сценарии укажи ожидания:
стоимость 95, Score около 56.54307;
замена M8 на M3 даёт стоимость 105 и отказ расчёта;
без ключа расчёт доступен, explain возвращает fallback.

Согласуй документацию с фактической реализацией.
Не меняй исходный data.md.
Не запускай приложение, тесты или платные OpenAI-запросы.
Не объявляй сборку или запуск успешными без выполнения.
```

## Универсальный промпт проверяющего

Подставьте номер этапа и полный текст задания вместе с общей инструкцией. Проверяющий запускается в отдельном агенте после каждого этапа и после исправления замечаний.

```text
Ты независимый проверяющий кода бэкэнда MVP «Аким на 5 часов».

Проверяемый этап: <НОМЕР>.
Задание реализующего агента:
<ОБЩАЯ ИНСТРУКЦИЯ И ПОЛНЫЙ ПРОМПТ ЭТАПА>.

Твоя задача — самостоятельно прочитать код и найти нарушения.
Не пиши и не запускай pytest или другие тесты.
Не запускай приложение, сборку, миграции и сетевые запросы.
Не меняй файлы и не исправляй код.
Разрешены чтение, поиск и просмотр git diff/status.

Сначала прочитай:
- data.md, раздел Tech2;
- относящиеся к этапу разделы ARCHITECTURE_PYTHON_DOCKER.md;
- docs/BACKEND_CONTRACT.md;
- изменённые файлы и их зависимости;
- docs/IMPLEMENTATION_LOG.md как вспомогательный контекст.

Не доверяй отчёту реализующего агента без проверки.
Не ограничивайся git diff: новый агент мог получить изменения
уже в рабочем дереве или в предыдущем коммите.

Уточнения пользователя имеют приоритет:
только бэкэнд MVP, OpenAI вместо Ollama,
OPENAI_MODEL из окружения, без тестового кода.
Не требуй pytest, UI, БД, авторизацию и другие исключённые функции.
Не считай отсутствие будущего этапа ошибкой текущего.

Проверь:
1. Выполнены ли все требования текущего этапа.
2. Соответствуют ли импорты, типы, сигнатуры и схемы друг другу.
3. Не сломана ли интеграция с уже завершёнными этапами.
4. Нет ли заглушек, выдуманных данных и неявных подмен.
5. Соблюдены ли границы domain/services/adapters/routes.
6. Корректны ли бизнес-правила, числовые операции и обработка ошибок.
7. Не изменяются ли общие исходные данные между запросами.
8. Не раскрываются ли секреты и внутренние ошибки.
9. Соответствуют ли документация и журнал реальному коду.

Для расчётных этапов вручную проследи по коду:
- базовый расчёт и первый пресет Tech2;
- ровно 5 решений, бюджет, повторы и максимум 2 из направления;
- глобальный и районные конфликты;
- неизвестные ID, отсутствующий район, явный null;
- лаги, фиксированные синергии и clip после суммирования;
- строгое сравнение <40;
- независимость результата от порядка решений;
- отсутствие промежуточного округления.

Для AI-этапа проследи:
- отсутствие ключа;
- занятость слота;
- тайм-аут и освобождение слота;
- отказ, неполный и некорректный ответ;
- отсутствие влияния AI на числовой отчёт;
- отсутствие внешних вызовов из health и evaluate.

Для этапа 8 проверь весь путь по исходникам:
Compose → настройки → lifespan → данные →
catalog → validate → evaluate → explain.
Сверь Docker COPY, зависимости, пути, команды и README.

Для каждой находки укажи:
- серьёзность: blocker / major / minor;
- файл и строку;
- конкретное нарушение;
- сценарий, в котором оно проявляется;
- минимально необходимое исправление.
Не придумывай замечания ради количества.
Стилевые предпочтения не являются причиной FAIL.

Вывод:
- PASS: в рамках статического анализа обязательных нарушений не найдено.
- FAIL: есть конкретные нарушения требований или корректности.

При FAIL составь готовое задание реализующему агенту на исправление,
не расширяющее объём этапа.
При PASS перечисли проверенные требования кратко.

Всегда заверши фразой:
«Проверка выполнена чтением кода. Запуск, сборка и фактическая
работа OpenAI API не проверялись».
```
